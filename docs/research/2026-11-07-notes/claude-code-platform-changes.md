## Key question 1: Hooks: events, stdin fields, env vars, CLAUDE_PROJECT_DIR in worktrees, hooks.json schema

### Takeaway
The hooks reference now lists **33 events** (up from the roughly dozen a May-2026 plugin would know), five handler types (`command`, `http`, `mcp_tool`, `prompt`, `agent`), new handler fields (`if`, `once`, `statusMessage`, `async`, `asyncRewake`, `onFailure`, exec-form `args`), and documents explicitly that **`CLAUDE_PROJECT_DIR` does NOT follow Claude into a worktree while the stdin `cwd` field does**. A persistent plugin data dir (`CLAUDE_PLUGIN_DATA`) and a per-session `scratchpad_dir` stdin field exist now.

**CLAUDE_PROJECT_DIR in worktrees (the documented semantics):**
- Worktrees page, note titled "Hook paths don't follow the worktree": "`${CLAUDE_PROJECT_DIR}` stays put: it still points at the project root where the session started, so a hook command such as `${CLAUDE_PROJECT_DIR}/.claude/hooks/check-style.sh` still runs the script in the main checkout. `cwd` follows Claude: the `cwd` field in the hook's input JSON is the worktree root, and it moves again when Claude runs `cd`. Read it when a hook needs the worktree path." — [Worktrees](https://code.claude.com/docs/en/worktrees)
- Desktop-app worktree sessions: "Claude Code reads project configuration such as settings, hooks, skills, agents, commands, and `.mcp.json` servers from the main checkout's root. Hook commands run in that root, and `${CLAUDE_PROJECT_DIR}` points at it. ... `CLAUDE.md` files and `.claude/rules/` still load from the worktree." — [Worktrees](https://code.claude.com/docs/en/worktrees)
- GitHub issue #84723 "Hooks: add CLAUDE_AGENT_ROOT_DIR (worktree-aware root), since today absolute and relative hook paths are each broken in a different way", opened 2026-08-07, labeled `area:hooks` on 2026-08-20 by bcherny, marked stale 2026-09-21, **closed as "not planned" by the bot on 2026-10-05** with no substantive maintainer reply. Quote: "`CLAUDE_PROJECT_DIR` is pinned to the **primary clone** and does not move for a worktree." and "an unresolvable command exits **127**, and any non-2 non-zero exit is a **non-blocking error**" — [Issue #84723](https://github.com/anthropics/claude-code/issues/84723)
- Hook security best practice: "Use absolute paths: specify full paths for scripts. In exec form, use `${CLAUDE_PROJECT_DIR}` and the path needs no quoting. In shell form, wrap it in double quotes" — [Hooks reference](https://code.claude.com/docs/en/hooks)

### Inferences
- A plugin that stores session state under `${CLAUDE_PROJECT_DIR}/.ytstack/...` from a hook will write into the **main checkout** when the session (or a subagent with `isolation: "worktree"`) runs in a worktree, while the model's own Write/Edit calls land in the worktree. To be worktree-correct, hooks must read `cwd` from stdin (or `git -C "$cwd" rev-parse --show-toplevel`) instead of `CLAUDE_PROJECT_DIR`.
- There is no official worktree-aware root variable and the request for one was closed, so the stdin `cwd` field is the only sanctioned way.
- `onFailure: "block"` (v2.1.295) closes the "exit 127 fails open" hole that #84723 complained about, for plugin authors who want fail-closed guards.
- `scratchpad_dir` (v2.1.257) is a new per-session location a hook could use for session-local temp files instead of the project tree, but the docs I read do not describe its lifecycle beyond "Session scratchpad path. Absent if none."

### Gaps
- I could not date when `Setup`, `WorktreeCreate`/`WorktreeRemove`, `CwdChanged`, `FileChanged`, `InstructionsLoaded`, `ConfigChange`, `PostToolBatch`, `MessageDisplay`, `UserPromptExpansion`, `PermissionDenied`, `PostCompact`, `StopFailure`, `PostToolUseFailure`, `Elicitation`/`ElicitationResult` were introduced; the changelog below v2.1.160 was not read. (Elicitation existed by v2.1.105 per a docs note.) Diff against the plugin's own May-2026 hook list to see which are new to it.
- The exact semantics/lifecycle of `scratchpad_dir` were not in the portion of the hooks page I read.
- Whether `CLAUDE_CODE_SESSION_ID` is formally listed on the hooks env-var table: not confirmed from the page text I could read; the changelog uses that name.

## Key question 2: Skills: SKILL.md frontmatter, substitutions, dynamic injection, description limits, deprecations

### Takeaway
Skills have absorbed custom commands; the frontmatter table now has ~20 fields including `when_to_use`, `arguments`, `disallowed-tools`, `effort`, `context: fork` + `agent` + `background`, `hooks`, `paths`, `shell`, `metadata`, `license`, `compatibility`. Description+`when_to_use` is capped at **1,536 chars** per entry, the whole listing at **1% of the context window** (configurable), SKILL.md body should stay **under 500 lines**, and `/skill-doctor` plus `claude plugin eval` exist to measure whether descriptions trigger.

### Cited Findings

**Frontmatter reference (current docs). Unrecognized fields are ignored without error in Claude Code; the opening `---` must be the first line; booleans accept `true/false/yes/no/on/off/1/0` (any case, added v2.1.218, 2026-07-22):**
- `name` (defaults to directory name), `description` (recommended; falls back to first non-empty body line), `when_to_use` ("Appended to `description` in the listing and counts toward the 1,536-character cap"), `argument-hint`, `arguments` (named positional args for `$name` substitution), `disable-model-invocation` (also blocks preloading into subagents and session-scoped scheduled tasks), `user-invocable` (default `true`), `allowed-tools` (grant clears on next user message), `disallowed-tools`, `model` (or `inherit`; with `context: fork` sets the subagent model), `effort` (`low|medium|high|xhigh|max`), `context` (`fork`), `agent` (default `general-purpose`), `background` (only with `context: fork`; default `true`), `hooks` (registered on invocation, persist for the session), `paths` (globs relative to cwd), `shell` (`bash` default or `powershell`), `metadata` (free-form, ignored), `license`, `compatibility` (≤500 chars, accepted but not acted on) — [Skills](https://code.claude.com/docs/en/skills); [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- Portability warning: "Fields outside the Agent Skills spec (`name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`) cause a hard error when a skill is packaged or uploaded to claude.ai, the Skills API, or via `package_skill.py`. ### Inferences
- ytstack's custom frontmatter keys (`tier`, `version`) are tolerated by Claude Code ("Unrecognized fields are ignored without error") but would break upload to claude.ai/Skills API; if cross-surface portability matters, move them under `metadata`.
- Because `when_to_use` counts against the same 1,536-char cap and the listing budget drops least-used descriptions first, long "thin wrapper" descriptions on many skills are now the main risk to triggering; `/skill-doctor` and `claude plugin details <plugin>` show the always-on cost.
- `context: fork` skills now run in the background by default; a skill that must return synchronously (e.g. a gate before "done") needs `background: false`.

### Gaps
- Introduction dates for `when_to_use`, `arguments`, `disallowed-tools`, `paths`, `${CLAUDE_SKILL_DIR}`, `compatibility`, `license` were not found in the v2.1.160+ changelog chunks I read; they may predate June 2026 or have shipped without a changelog line.
- The skills page portion I read did not state a numeric maximum skill count.

- For a plugin distributed via a GitHub marketplace, the manifest `version` is the release switch: no bump = no update for users, however many commits land. Pair `claude plugin tag` with the bump.

## Key question 4: Agent teams, subagents, worktrees, memory

### Takeaway
Agent teams are **still experimental** behind `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`; a named Agent-tool spawn now auto-launches as a teammate when the flag is on; `TeamCreate`/`TeamDelete` tools and `teammateDefaultModel` were removed. ## Key question 5: Official guidance on where plugins store session-local state and on hooks writing files

### Takeaway
There is **no explicit official rule saying "don't write plugin state into the project working tree"**. What the docs do say: durable plugin state goes in `${CLAUDE_PLUGIN_DATA}`, never `${CLAUDE_PLUGIN_ROOT}`; hooks get the worktree via stdin `cwd` while `CLAUDE_PROJECT_DIR` is pinned to the launch root; Claude Code's own per-session/per-project state lives under `~/.claude/` (projects, teams, tasks, agent-memory, worktrees under `.claude/worktrees/`), and `scratchpad_dir` exists as a per-session path.

### Cited Findings
- "`${CLAUDE_PLUGIN_ROOT}` changes when the plugin updates, so don't write state there." and "`${CLAUDE_PLUGIN_DATA}`: a directory that survives updates, for `node_modules`, virtual environments, and caches. It resolves to `~/.claude/plugins/data/<id>/` and is created when first referenced" — [Manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference); [Plugin components](https://code.claude.com/docs/en/plugins/components)
- Hook stdin `cwd` "Follows Claude into a worktree and after `cd`"; `CLAUDE_PROJECT_DIR` "Does not move into a worktree"; `scratchpad_dir` "Session scratchpad path. Absent if none. Requires v2.1.257+" — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Worktree isolation blocks model-driven `Edit`/`Write` into the main checkout but "None of them tracks which files a shell command writes, so a command that writes into the main checkout without running git there, such as `cp` or a shell redirect, isn't refused" — i.e. a hook script can still write into the main checkout — [Worktrees](https://code.claude.com/docs/en/worktrees)
- Claude Code's own session-local state locations: `~/.claude/projects/<project>/memory/` (auto memory, shared across worktrees), `~/.claude/projects/{project}/{sessionId}/subagents/`, `~/.claude/teams/{team}/` (removed at session end), `~/.claude/tasks/{team}/` (kept, swept by `cleanupPeriodDays`), `~/.claude/plugins/data/<id>/`, `.claude/agent-memory/<agent>/` (committable) and `.claude/agent-memory-local/<agent>/` (gitignored), `.claude/worktrees/<name>/` (recommended gitignore) — [Memory](https://code.claude.com/docs/en/memory); [Subagents](https://code.claude.com/docs/en/sub-agents); [Agent teams](https://code.claude.com/docs/en/agent-teams); [Plugin loading](https://code.claude.com/docs/en/plugins/loading); [Worktrees](https://code.claude.com/docs/en/worktrees)
- Hook security best practices: "Validate and sanitize inputs", "Always quote shell variables", "Block path traversal: check for `..` in file paths", "Use absolute paths", "Skip sensitive files" — [Hooks reference](https://code.claude.com/docs/en/hooks)
- The only event the docs describe as a place for "saving session state" is `SessionEnd` ("Useful for cleanup tasks, logging session statistics, or saving session state"), which has a 1.5 s default budget; `PreCompact` is documented as a hook whose stdout becomes compaction instructions, not as a state-saving point — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Eval runs load nothing project-level and use a temporary `HOME`, so plugin code that assumes `~/.claude/...` or `.ytstack/` exists must create it or tolerate absence — [Plugin evals](https://code.claude.com/docs/en/plugin-evals)
- Sandboxed Bash could not write to project dirs named `hooks/` or `config/` until v2.1.275 fixed it — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- Community issue pattern: hooks pointing at `$CLAUDE_PROJECT_DIR/.claude/helpers/` fail in worktrees because untracked `.claude/` content isn't in the worktree; `.worktreeinclude` and the skills/agents/commands read-through (v2.1.277) are the official mitigations — [Worktrees](https://code.claude.com/docs/en/worktrees); [Issue #84723](https://github.com/anthropics/claude-code/issues/84723)

### Inferences
- A workflow plugin that writes artifacts into the repo on purpose (`.ytstack/`, HANDOFF.md) is not contradicted by any doc, but it should (a) resolve the target from hook `cwd`, not `CLAUDE_PROJECT_DIR`, so the artifact lands in the checkout being worked on, and (b) keep anything that is per-machine or per-session (locks, caches, last-run markers) in `${CLAUDE_PLUGIN_DATA}` or `scratchpad_dir`.
- A `SessionEnd` hook that writes a handoff file has 1.5 s by default; set a per-hook `timeout` (raises the budget to that value, max 60 s) or use `PreCompact`/`Stop` instead.

### Gaps
- No official page states a policy on plugins writing to the user's repository; this is an absence, not a finding.
- `scratchpad_dir` lifecycle (who creates it, when it is cleaned) is undocumented in the pages I read.
