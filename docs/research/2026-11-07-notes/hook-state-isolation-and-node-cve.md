# TOPIC A -- Worktree-aware hooks and session-state storage

## A1. Claude Code: what hook stdin contains today, and what `cwd` / `CLAUDE_PROJECT_DIR` mean in worktrees and subagents

### Takeaway
Hook stdin always carries `session_id`, `cwd`, `transcript_path`, `permission_mode`, `hook_event_name` (plus `prompt_id`, `scratchpad_dir`, `effort`, `agent_id`/`agent_type` where applicable). `cwd` is "where Claude is working" and follows both `EnterWorktree` and `cd`; `CLAUDE_PROJECT_DIR` is frozen at the session's start directory and does NOT move into a worktree. That asymmetry is exactly what makes a hook that anchors on `CLAUDE_PROJECT_DIR` write into the main checkout while the agent works in a linked worktree.

### Cited Findings
- Common input fields documented for every hook event: `session_id`, `prompt_id` (UUID of the prompt, absent until first user input), `transcript_path` ("Path to the conversation JSON. The file is written asynchronously and may lag"), `cwd` ("Current working directory when the hook is invoked"), `scratchpad_dir` (session scratchpad dir, absent if none, requires v2.1.257+), `permission_mode` (`"default"|"plan"|"acceptEdits"|"auto"|"dontAsk"|"bypassPermissions"`), `effort` (object with `level`), `hook_event_name`; `agent_id` and `agent_type` identify the (sub)agent a hook fired in. -- [Claude Code hooks reference](https://code.claude.com/docs/en/hooks)
- Documented `cwd` semantics: "After Claude enters a worktree, `cwd` is the worktree root. After Claude runs `cd`, it is the new directory. Hooks should read `cwd` when they need to know where Claude is working." -- [hooks](https://code.claude.com/docs/en/hooks)
- `CLAUDE_PROJECT_DIR` = "the project root where the session started." "It does not move when Claude enters a worktree." -- [hooks](https://code.claude.com/docs/en/hooks)
- Worktrees page, explicit note "Hook paths don't follow the worktree": "`${CLAUDE_PROJECT_DIR}` stays put: it still points at the project root where the session started, so a hook command such as `${CLAUDE_PROJECT_DIR}/.claude/hooks/check-style.sh` still runs the script in the main checkout. `cwd` follows Claude: the `cwd` field in the hook's input JSON is the worktree root, and it moves again when Claude runs `cd`. Read it when a hook needs the worktree path." -- [Worktrees](https://code.claude.com/docs/en/worktrees)
- Desktop-app worktree sessions: "Claude Code reads project configuration such as settings, hooks, skills ... from the main checkout's root. Hook commands run in that root, and `${CLAUDE_PROJECT_DIR}` points at it. To reach the files Claude is working on, read the worktree's path from the hook's `cwd` input field." -- [Worktrees](https://code.claude.com/docs/en/worktrees)
- PreToolUse/PostToolUse carry `tool_name`, `tool_input`, `tool_use_id`; PostToolUse additionally `tool_response` and `duration_ms`. Bash `tool_response` is "an object with `stdout`, `stderr`, `interrupted`, and `isImage` fields", optionally `bashEditDiff` (v2.1.269+, beta). Example Bash `tool_input`: `{"command": "npm test", "description": "...", "timeout": 120000, "run_in_background": false}`. -- [hooks](https://code.claude.com/docs/en/hooks)
- Where Bash runs: in the main session, `cd` persists between Bash calls (so `cwd` in the next hook is the new directory). In subagents: "A subagent starts in the main conversation's current working directory. Within a subagent, `cd` commands don't persist between Bash or PowerShell tool calls and don't affect the main conversation's working directory." -- [Subagents](https://code.claude.com/docs/en/sub-agents)
- `isolation: worktree` subagents: "A subagent with `isolation: worktree` runs its Bash and PowerShell commands inside its worktree. A command whose working directory resolves to your main checkout instead ... fails with an error." The worktree is "branched by default from your default branch rather than the parent session's `HEAD`" and "automatically cleaned up if the subagent makes no changes." -- [Subagents](https://code.claude.com/docs/en/sub-agents)
- Hooks inside subagents: "Hooks from settings files, managed policy settings, and plugins all apply inside subagents, so a `PreToolUse` hook in `settings.json` also runs before every tool a subagent uses." Subagent `Stop` frontmatter hooks become `SubagentStop`. -- [Subagents](https://code.claude.com/docs/en/sub-agents)
- SubagentStop input: `stop_hook_active`, `agent_id`, `agent_type`, `agent_transcript_path`, `last_assistant_message`; "The `transcript_path` is the main session's transcript, while `agent_transcript_path` is the subagent's own transcript stored in a nested `subagents/` folder." Subagent transcript path shape: `~/.claude/projects/{project}/{sessionId}/subagents/agent-{agentId}.jsonl`. -- [hooks](https://code.claude.com/docs/en/hooks), [Subagents](https://code.claude.com/docs/en/sub-agents)
- Worktree default location and naming: "By default, the worktree is created under `.claude/worktrees/<name>/` at your repository root, on a new branch named `worktree-<name>`"; tip: "Add `.claude/worktrees/` to your `.gitignore`". `EnterWorktree` to a path outside `.claude/worktrees/` prompts for approval; "The move takes the session's working directory, write access, and project configuration such as `CLAUDE.md` and settings to that location." -- [Worktrees](https://code.claude.com/docs/en/worktrees)
- Isolation enforcement (applies to `--worktree`, `EnterWorktree`, resumed worktree sessions and every subagent spawned from them): blocks Edit/Write into the main checkout, blocks Bash whose working directory resolves to the main checkout, blocks git redirected into the main checkout (`git -C`, `--git-dir`, `GIT_DIR`, `GIT_WORK_TREE`, `cd`). BUT: "None of them tracks which files a shell command writes, so a command that writes into the main checkout without running git there, such as `cp` or a shell redirect, isn't refused by them." -- [Worktrees](https://code.claude.com/docs/en/worktrees)
- Worktree lifecycle hook events: `WorktreeCreate` input adds `name` (slug, e.g. `bold-oak-a3f2`); command hooks must print the created path on stdout (HTTP hooks: `hookSpecificOutput.worktreePath`). "A WorktreeCreate hook doesn't run for a worktree Claude adds through Bash", and a plugin's WorktreeCreate hook does not run with `--worktree --tmux` (plugins load after creation; before v2.1.300 not even with `--worktree` alone). `WorktreeRemove` input adds `worktree_path`; "When a subagent or a workflow agent finishes, Claude Code keeps the worktree your WorktreeCreate hook made for it and doesn't run your WorktreeRemove hook." -- [hooks](https://code.claude.com/docs/en/hooks)
- `CwdChanged` event: input adds `old_cwd` and `new_cwd`; no matchers, "fires on every occurrence"; cannot block; has access to `CLAUDE_ENV_FILE` and vars written there "persist into subsequent Bash commands until the next CwdChanged event, when Claude Code clears them." -- [hooks](https://code.claude.com/docs/en/hooks)
- `CLAUDE_ENV_FILE`: "SessionStart hooks have access to the `CLAUDE_ENV_FILE` environment variable, which provides a file path where you can persist environment variables for the shell commands Claude runs later in the session." Available for `SessionStart`, `Setup`, `CwdChanged`, `FileChanged` only; "Each Bash command runs the file's contents as shell code before the command itself." -- [hooks](https://code.claude.com/docs/en/hooks)
- Hook execution directory fallback: hooks run in the current directory; if it was deleted mid-session they fall back to the session start directory, project root, home, or temp dir and log a warning. -- [hooks](https://code.claude.com/docs/en/hooks)
- Full event list (33): SessionStart, Setup, UserPromptSubmit, UserPromptExpansion, PreToolUse, PermissionRequest, PermissionDenied, PostToolUse, PostToolUseFailure, PostToolBatch, Notification, MessageDisplay, SubagentStart, SubagentStop, TaskCreated, TaskCompleted, Stop, StopFailure, TeammateIdle, InstructionsLoaded, ConfigChange, CwdChanged, DirectoryAdded, FileChanged, WorktreeCreate, WorktreeRemove, PreCompact, PostCompact, PreModelSwitch, PostModelSwitch, Elicitation, ElicitationResult, SessionEnd. -- [hooks](https://code.claude.com/docs/en/hooks)
- SessionStart input `source` is `"startup"|"resume"|"clear"|"compact"|"fork"`; PreCompact input adds `trigger` (`manual`/`auto`) and `custom_instructions`; SessionEnd adds `reason` and has a 1.5 s default timeout (override via per-hook `timeout` or `CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS`). -- [hooks](https://code.claude.com/docs/en/hooks)
- Plugin env vars exported to hook processes: `CLAUDE_PLUGIN_ROOT`, `CLAUDE_PLUGIN_DATA`, `CLAUDE_PROJECT_DIR`, `CLAUDE_PLUGIN_OPTION_<KEY>`. "The variables aren't present in the environment of commands Claude runs through the Bash tool, in the main session or in a subagent." -- [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- Worktree transcript binding: when Claude enters/exits a git worktree Claude Code created, "Claude Code records the session under the session's new working directory, the same way `/cd` does, so `/desktop` and `--resume` find it there." Resume re-enters the worktree. -- [Worktrees](https://code.claude.com/docs/en/worktrees)

### Inferences
- In a plugin hook, treat `cwd` (stdin) as "where the agent is working" and `CLAUDE_PROJECT_DIR` as "where the session was launched". For per-repo state, derive the repo identity from `cwd` via git (see A3), never from `CLAUDE_PROJECT_DIR`.
- There is no hook-visible field telling you which worktree a Bash command ran in beyond `cwd`; if the command itself does `cd <dir> && ...`, the hook only sees the pre-command `cwd` in PreToolUse and the post-command `cwd` in PostToolUse (the main session persists `cd`). Parsing `tool_input.command` for a leading `cd` is heuristic; the docs give no structured field for it.
- `CLAUDE_ENV_FILE` plus `CwdChanged` is a documented way to push a per-worktree env var (e.g. `YT_STATE_DIR`) into every later Bash command and have it cleared on the next cwd change; but it is NOT visible to other hook events, so hooks must recompute from `cwd`.
- The ytstack repo's current hooks (`hooks/pre-compact`, `hooks/post-tool-use-bash`, `hooks/session-end`, etc.) anchor on `PROJECT_DIR="${CLAUDE_PROJECT_DIR:-$PWD}"` and write `HANDOFF.md` into `$PROJECT_DIR/.ytstack/`; combined with the documented "CLAUDE_PROJECT_DIR stays put" behaviour this writes into the main checkout while the agent works in a worktree (verified by reading `/Users/alex/Sync/home/alex/Code/WebDev/projects/yesterday-ai/ytstack/hooks/pre-compact` lines 15-30).

### Gaps
- The docs do not state whether `session_id` in a subagent's hooks equals the parent session id (Codex documents this explicitly; Claude Code does not in the fetched text). Observable via `agent_id` presence instead.
- No documented field for the Bash tool's effective working directory when the command contains its own `cd`.

## A2. Claude Code: documented per-session / per-project state directories a plugin can use

### Takeaway
Claude Code documents four candidate locations: the per-session `scratchpad_dir` (temp dir, swept with the transcript, only for claude.ai-login sessions), `~/.claude/projects/<encoded-cwd>/` (transcripts + auto memory; encoding is path with non-alphanumerics replaced by `-`), `${CLAUDE_PLUGIN_DATA}` (= `~/.claude/plugins/data/<id>/`, survives updates, deleted on uninstall) and `~/.claude/sessions/` (one small lock-ish file per running session, used for concurrency/crash detection). None of these is inside the working tree, so all keep `git status` clean.

### Cited Findings
- `${CLAUDE_PLUGIN_DATA}` resolves to `~/.claude/plugins/data/<id>/`, "created on first reference and kept across plugin updates"; `<id>` is the plugin identifier with every char other than letter/digit/`_`/`-` replaced by `-`. Intended for "Installed dependencies such as `node_modules`, generated code, and caches". "`${CLAUDE_PLUGIN_ROOT}` changes when the plugin updates, so don't write state there." Deleted on uninstall unless `--keep-data`. -- [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference)
- Scratchpad: "per-session directory that Claude Code gives Claude for temporary files"; macOS path `/private/tmp/claude-<uid>/<project>/<session-id>/scratchpad/`, Linux `/tmp/claude-<uid>/<project>/<session-id>/scratchpad/`; "`<project>` is your working directory path with every character other than letters and digits replaced by `-`, such as `-Users-you-my-project`"; "Hooks receive the current session's path as `scratchpad_dir`"; exists only when signed in with claude.ai account, using Anthropic API, `enableArtifact` not false; swept when the transcript is swept and the OS may clear it on reboot. -- [.claude directory](https://code.claude.com/docs/en/claude-directory)
- `~/.claude/projects/<project>/<session>.jsonl` transcript; `projects/<project>/<session>/subagents/`, `/tool-results/`, `/mcp-tasks/`; `projects/<project>/memory/` auto memory (not swept while non-empty); `session-env/` "Per-session environment metadata"; `tasks/`; `shell-snapshots/`. Default `cleanupPeriodDays` 30 (min 1). -- [.claude directory](https://code.claude.com/docs/en/claude-directory)
- `sessions/`: "holds one small file per running session, used to detect concurrent sessions and crashes. It isn't part of the age-based sweep: Claude Code removes each file when its session exits and clears crash leftovers on the next launch." -- [.claude directory](https://code.claude.com/docs/en/claude-directory). Verified locally: `~/.claude/sessions/` contains `<pid>.json` (e.g. `{"peerToken":"...","procStart":"Thu Nov  5 21:14:04 2026","pidDomain":"darwin"}`) plus `<pid>.<sha256>.key` files.
- `CLAUDE_CONFIG_DIR` relocates all of `~/.claude` and `~/.claude.json`; it cannot be set from project/local settings. -- [.claude directory](https://code.claude.com/docs/en/claude-directory), [env vars](https://code.claude.com/docs/en/env-vars)
- `CLAUDE_CODE_CHILD_SESSION=1` is set in Bash/PowerShell/Monitor subprocesses so a nested `claude` is excluded from `--resume`/history; `CLAUDE_CODE_BRIDGE_SESSION_ID` is set in Bash and hook subprocesses only while Remote Control is active (v2.1.199+). -- [env vars](https://code.claude.com/docs/en/env-vars)
- Historical pollution incidents: issue #54452 "Move per-session runtime state out of workspace `.claude/` into `~/.claude/projects/<encoded>/`" (opened 2026-04-28, closed 2026-05-02) complains that `.claude/scheduled_tasks.lock` (`{"sessionId":...,"pid":...,"procStart":...}`) lands in the committed `.claude/` dir and forces "fine-grained gitignore entries"; proposed fix: use `~/.claude/projects/<encoded-workspace-path>/`. -- [anthropics/claude-code#54452](https://github.com/anthropics/claude-code/issues/54452) (read via `gh`). Issue #31984 (2026-03-08, closed same day) reports an undocumented `.claire/worktrees/...` dir appearing untracked when using `isolation: "worktree"`. -- [anthropics/claude-code#31984](https://github.com/anthropics/claude-code/issues/31984). Issue #944: CLI auto-added `**/.claude/settings.local.json` to a checked-in `.gitignore`; reporter asked for `.git/info/exclude` instead. -- [anthropics/claude-code#944](https://github.com/anthropics/claude-code/issues/944). github/gitignore PR #4895 proposes adding `.claude/worktrees/` to `Agents.gitignore`. -- [github/gitignore#4895](https://github.com/github/gitignore/pull/4895)

### Inferences
- For ytstack's volatile artefacts (HANDOFF.md written by pre-compact, journals, drafts), `${CLAUDE_PLUGIN_DATA}/projects/<repo-key>/<session_id>/` is the documented, update-safe, out-of-tree home when running under Claude Code. Under Codex the equivalent is `PLUGIN_DATA` (see A4). A plugin-independent fallback (XDG, A5) is still needed for hooks launched outside either plugin system.
- `scratchpad_dir` is unsuitable for handoff breadcrumbs: it is absent for API-key users and may vanish on reboot.
- The `~/.claude/projects/<encoded>` encoding (replace non-alphanumerics with `-`) collides for paths that differ only in punctuation and is keyed to the launch cwd, so a linked worktree gets a different `<project>` than the main checkout. That is good for session separation but bad for "same repo" grouping; a repo key derived from `--git-common-dir` groups worktrees correctly (A3).

### Gaps
- No documented public API for writing into `~/.claude/projects/<project>/` from a plugin; it is Claude Code's own data dir. Using it is "community practice", not documented behaviour.

## A3. Git: reliable detection recipes (main vs linked worktree, bare, submodule) and which checks are wrong

### Takeaway
Use `git rev-parse --path-format=absolute --git-dir` vs `--git-common-dir`: they differ iff you are in a linked worktree (git >= 2.31 for `--path-format`). `[ -d .git ]` is wrong because in a linked worktree (and in a submodule) `.git` is a FILE containing `gitdir: ...`, and in a subdirectory `.git` is absent. Derive a repo key from the absolute common dir (shared by all worktrees of one repo), and a worktree key from `--show-toplevel`.

### Cited Findings
- `--git-dir`: "Show `$GIT_DIR` if defined. Otherwise show the path to the .git directory. The path shown, when relative, is relative to the current working directory." `--git-common-dir`: "Show `$GIT_COMMON_DIR` if defined, else `$GIT_DIR`." `--show-toplevel`: "Show the (by default, absolute) path of the top-level directory of the working tree. If there is no working tree, report an error." `--is-inside-work-tree`, `--is-inside-git-dir`, `--is-bare-repository` print `true`/`false`. `--path-format=(absolute|relative)`: "If specified as absolute, the paths printed by those options will be absolute and canonical ... The default is option specific"; affects `--git-dir`, `--git-common-dir`, `--resolve-git-dir`, `--git-path`, `--show-toplevel`, `--show-superproject-working-tree`, `--shared-index-path`. `--absolute-git-dir` = `--git-dir` but always canonical absolute. `--show-superproject-working-tree` outputs nothing if not a submodule. -- [git-rev-parse](https://git-scm.com/docs/git-rev-parse)
- `--path-format` was introduced in Git 2.31 (2021): the 2.32-rc1 notes mention the option "introduced in v2.31 era"; a Fuchsia jiri commit says "the --path-format flag was only added to git in version 2.31.0". -- [git 2.32-rc1 notes](https://googlers.googlesource.com/jrn/git/+/refs/tags/v2.32.0-rc1%5E%21/), [jiri compat commit](https://Fuchsia.googlesource.com/jiri/+/9380e042126af6a8c76732b681bd2bdddb920594%5E%21/)
- Worktree internals: "Each linked worktree has a private sub-directory in the repository's `$GIT_DIR/worktrees` directory ... Within a linked worktree, `$GIT_DIR` is set to point to this private directory (e.g. `/path/main/.git/worktrees/test-next`) and `$GIT_COMMON_DIR` is set to point back to the main worktree's `$GIT_DIR` (e.g. `/path/main/.git`). These settings are made in a `.git` file located at the top directory of the linked worktree." Rule of thumb: "do not make any assumption about whether a path belongs to `$GIT_DIR` or `$GIT_COMMON_DIR` ... Use `git rev-parse --git-path`". -- [git-worktree](https://git-scm.com/docs/git-worktree)
- `git worktree list --porcelain`: one attribute per line, first line `worktree <path>`, then `HEAD <sha>`, `branch <ref>` or `detached`, optional `bare`, `locked [reason]`, `prunable [reason]`; records separated by blank line; `-z` NUL-terminates so paths with newlines parse; porcelain "will remain stable across Git versions and regardless of user configuration." -- [git-worktree](https://git-scm.com/docs/git-worktree)
- Submodules + worktrees: "Multiple checkout in general is still experimental, and the support for submodules is incomplete. It is NOT recommended to make multiple checkouts of a superproject." -- [git-worktree](https://git-scm.com/docs/git-worktree)
- Verified locally (git 2.56.0, macOS, script `/tmp/wt-probe.sh`):
  - main checkout: `--git-dir` = `.git` (relative!), `--git-common-dir` = `.git`, `.git` is a dir.
  - linked worktree root: `--git-dir` = `/private/tmp/.../main/.git/worktrees/linked` (absolute even without `--path-format`), `--git-common-dir` = `/private/tmp/.../main/.git`, `.git` is a FILE with content `gitdir: /private/tmp/.../main/.git/worktrees/linked`; `.git/worktrees/linked/` contains `commondir` (`../..`), `gitdir` (path to the worktree's `.git` file), `HEAD`, `index`, `logs`, `ORIG_HEAD`, `refs`.
  - subdirectory of a linked worktree: `.git` absent; `--show-toplevel` still returns the worktree root.
  - bare repo: `--is-bare-repository` = `true`, `--is-inside-work-tree` = `false`; a worktree added from a bare repo has `--git-common-dir` = `/.../bare.git` and `--git-dir` = `/.../bare.git/worktrees/from-bare` (so the main/linked test "git-dir != common-dir" says "linked", which is correct: every checkout of a bare repo is a linked worktree).
  - submodule: `.git` is a FILE, `--git-dir` = `--git-common-dir` = `/.../main/.git/modules/mod` (so NOT detected as linked worktree), `--show-superproject-working-tree` = `/.../main`.
  - macOS: `/tmp` is a symlink to `/private/tmp`; `pwd` prints `/tmp`, `pwd -P` and git's absolute output print `/private/tmp`. Compare canonicalised paths only.
- Mixed relative/absolute default output of `--git-dir` (relative `.git` in main, absolute path in linked) is the documented "option specific" default; it is why naive string comparison of `--git-dir` vs `--git-common-dir` without `--path-format=absolute` happens to work in both cases here but is fragile. -- [git-rev-parse](https://git-scm.com/docs/git-rev-parse) + local probe.

### Inferences
- Recommended recipe (bash 3.2 compatible; no arrays, no `${var,,}`, no `mapfile`; git >= 2.31 for `--path-format`, with fallback):

```sh
#!/bin/bash
# usage: eval "$(yt_git_ctx [dir])"  -> sets YT_IN_GIT, YT_TOPLEVEL, YT_COMMON_DIR, YT_GIT_DIR, YT_IS_LINKED, YT_IS_BARE
yt_git_ctx() {
  dir="${1:-$PWD}"
  if ! git -C "$dir" rev-parse --is-inside-work-tree >/dev/null 2>&1; then
    echo 'YT_IN_GIT=0'; return 0
  fi
  if git -C "$dir" rev-parse --path-format=absolute --git-dir >/dev/null 2>&1; then
    gd=$(git -C "$dir" rev-parse --path-format=absolute --git-dir)
    cd_=$(git -C "$dir" rev-parse --path-format=absolute --git-common-dir)
  else   # git < 2.31: make relative output absolute by hand
    gd=$(git -C "$dir" rev-parse --absolute-git-dir)
    cd_=$(git -C "$dir" rev-parse --git-common-dir)
    case "$cd_" in /*) ;; *) cd_=$(cd "$dir" && cd "$cd_" && pwd -P) ;; esac
  fi
  top=$(git -C "$dir" rev-parse --show-toplevel 2>/dev/null)
  linked=0; [ "$gd" != "$cd_" ] && linked=1
  printf 'YT_IN_GIT=1\nYT_GIT_DIR=%s\nYT_COMMON_DIR=%s\nYT_TOPLEVEL=%s\nYT_IS_LINKED=%s\n' "$gd" "$cd_" "$top" "$linked"
}
```
  - `YT_IS_LINKED=1` means: this checkout is a linked worktree (or any worktree of a bare repo). Submodules correctly report 0 (their git-dir equals their common dir).
  - Pass the hook's `cwd` (from stdin JSON) as `dir`; do not `cd "$CLAUDE_PROJECT_DIR"` first.
- Repo key for state partitioning: hash of `YT_COMMON_DIR` (identical for main + all linked worktrees of one repo) e.g. `printf '%s' "$YT_COMMON_DIR" | shasum -a 256 | cut -c1-12` (`shasum` ships with macOS; `sha256sum` does not), optionally prefixed with `basename "$(dirname "$YT_COMMON_DIR")"` for human readability. Worktree key: hash of `YT_TOPLEVEL`. Avoid `basename "$(git rev-parse --show-toplevel)"` alone (what ytstack hooks use today as `SLUG`): two repos named `api` collide, and a worktree checked out at `.claude/worktrees/feature-x` yields slug `feature-x`.
- To ask "is `cwd` the main checkout or a linked worktree of repo X" in one shot: `git -C "$cwd" worktree list --porcelain -z` and compare the FIRST record's `worktree` path (git lists the main worktree first; from the local probe the main checkout appeared first) against `YT_TOPLEVEL`; but the ordering guarantee is not stated in the docs, so prefer the git-dir/common-dir comparison above.
- Wrong checks and why: `[ -d .git ]` fails in linked worktrees and submodules (`.git` is a file) and in subdirectories (absent). `[ -e .git ]` at `$PWD` fails in subdirectories. Grepping `.git` for `gitdir:` works for linked worktrees but also matches submodules; use `--git-common-dir`. Comparing `--git-dir` output to the literal `.git` breaks under `GIT_DIR` env or when run from a subdirectory. Not canonicalising (`/tmp` vs `/private/tmp`, trailing slashes, symlinked home) produces false "different repo" results on macOS.

### Gaps
- Git docs do not promise the main worktree is listed first in `git worktree list`; relying on it is an observation.
- Behaviour for `core.worktree` redirects and `GIT_WORK_TREE` overrides was not probed.

## A4. OpenAI Codex CLI: hooks, cwd/env semantics, worktrees

### Takeaway
Codex has shipped hooks (14 events) with a stdin schema deliberately shaped like Claude Code's (`session_id`, `transcript_path`, `cwd`, `hook_event_name`, `permission_mode`, `tool_name`, `tool_input`, `tool_response`), but `cwd` is documented as "Working directory for the session" (session-scoped, not tool-call-scoped), there is no `CwdChanged`/`WorktreeCreate`/`WorktreeRemove`, and the only hook env vars documented are the plugin ones (`PLUGIN_ROOT`, `PLUGIN_DATA`, with `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA` set for compatibility). ## A5. XDG state conventions, repo-slug derivation, and concurrency-safe journals

### Takeaway
XDG defines `$XDG_STATE_HOME` (default `~/.local/state`) exactly for "logs, history, recently used files ... current state of the application that can be reused on a restart"; macOS has no official position, libraries split between `~/Library/Application Support` and `~/.local/state`, and CLI-tool practice (incl. ytstack's own `~/.ytstack`) leans to dotdirs/XDG. For journals, POSIX only guarantees non-interleaving for pipe writes <= PIPE_BUF; for regular files it says "use some form of concurrency control", so the robust pattern is one file per session (no shared writer) or an `mkdir` lock; macOS ships no `flock(1)` by default (Homebrew one exists) but does ship `/usr/bin/shlock`.

### Cited Findings
- XDG Base Directory Spec v0.8 (2021-05-08): `$XDG_STATE_HOME` "defines the base directory relative to which user-specific state files should be stored", for "state data that should persist between (application) restarts" but not portable enough for DATA_HOME, examples "actions history (logs, history, recently used files, ...)" and "current state of the application that can be reused on a restart (view, layout, open files, undo history, ...)"; default `$HOME/.local/state`. `$XDG_CACHE_HOME` default `~/.cache`; `$XDG_DATA_HOME` default `~/.local/share`; `$XDG_CONFIG_HOME` default `~/.config`; `$XDG_RUNTIME_DIR` must be user-owned, mode 0700, no default. "All paths set in these environment variables must be absolute"; relative values "should consider the path invalid and ignore it." -- [freedesktop basedir spec](http://specifications.freedesktop.org/basedir/latest/)
- macOS mapping is unsettled: Go `adrg/xdg` maps the state dir to `~/Library/Application Support`; Rust `user_dirs` returns no state dir on macOS; a blog argues CLI tools should use XDG dirs on macOS rather than Application Support (GUI convention); forum guidance "use ~/Library/Application Support if XDG vars are unset on macOS." -- [adrg/xdg](https://gitea.com/rc-chuah/tea/src/branch/master/vendor/github.com/adrg/xdg), [user_dirs crate](https://docs.rs/user_dirs), [feedbagel (blog)](https://feedbagel.com/post/why-macos-command-line-tools-should-use-xdg-specification-instead-of-application), [aliquote (blog)](https://aliquote.org/post/xdg-specs-on-macos/)
- POSIX `write()`: with O_APPEND "the file offset shall be set to the end of the file prior to each write and no intervening file modification operation shall occur between changing the file offset and the write operation"; "Write requests of {PIPE_BUF} bytes or less shall not be interleaved with data from other processes" (pipes/FIFOs); the standard "does not specify the behavior of concurrent writes to a regular file from multiple threads, except that each write is atomic" and "Applications should use some form of concurrency control." -- [POSIX write()](https://pubs.opengroup.org/onlinepubs/9699919799/functions/write.html)
- Practice: PIPE_BUF is 4096 on Linux, POSIX minimum 512; appends under that size "usually don't tear" on local filesystems but not on NFS, and a telemetry post documented two >4 KiB events producing one spliced line. -- [StackOverflow "Is file append atomic in UNIX?" (mirror)](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/a/35260110), [blog: two events, one mangled line](https://blog-570662.gitlab.io/two-events-one-mangled-line/)
- Locks in shell: `mkdir` is "the only portable atomic transaction available to shell scripts"; check-then-create lockfiles race; `set -C` (noclobber) + `: > file` is an alternative; stale locks need `trap`/PID checks; Flutter fell back from `flock` to `shlock` then `mkdir`. -- [BashFAQ/045](https://mywiki.wooledge.org/BashFAQ/045?action=raw), [flutter shlock revert](https://flutter.googlesource.com/mirrors/flutter/+/5267d9877248f2531e5e6e4a1619eded8b6ae0ce%5E%21/), [SO: flock on macOS (mirror)](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/10526651/mac-os-x-equivalent-of-linux-flock-1-command)
- Verified locally (macOS, /bin/bash 3.2.57): `flock` resolves to `/opt/homebrew/bin/flock` (Homebrew, not stock); `/usr/bin/shlock` exists; `set -C; : > f` refuses the second create ("cannot overwrite existing file"); `mkdir` refuses the second create. Both work in bash 3.2.
- How other plugins store memory/handoffs:
  - superpowers: no project-local state; SessionStart hook only injects `skills/using-superpowers/SKILL.md` as `additionalContext`, with a legacy warning about `~/.config/superpowers/skills` (verified by reading `vendor/superpowers/hooks/session-start`).
  - gstack: global state in `~/.gstack/` (config.yaml, analytics), project-local `.gstack/` and `.gstack-worktrees` directories inside the repo (uninstall docs: `rm -rf .gstack .gstack-worktrees .claude/skills/gstack`) -- [gstack README (vendored)](/Users/alex/Sync/home/alex/Code/WebDev/projects/yesterday-ai/ytstack/vendor/gstack/README.md) lines 310, 329, 341, 430.
  - claude-mem: all data under `~/.claude-mem/` (settings.json, SQLite `memory.db`, `chroma/`), hooks on SessionStart/UserPromptSubmit/PostToolUse/Stop/SessionEnd via plugin `hooks/hooks.json`; nothing written into the repo. -- [claude-mem docs](https://docs.claude-mem.ai/configuration/hooks) (mixed official/third-party pages)
  - GSD (get-shit-done): original repo retired to [open-gsd/gsd-core](https://github.com/open-gsd/gsd-core); README says "structured artifacts like `STATE.md` and `CONTEXT.md` survive session boundaries" (committed project artefacts, no gitignore guidance found). -- [gsd-core README](https://raw.githubusercontent.com/open-gsd/gsd-core/main/README.md)
  - Conductor (Gemini CLI extension): state in a committed `conductor/` dir (`conductor/tracks/<track_id>/plan.md`); setup guides say to commit it. -- [Google developers blog](https://developers.googleblog.com/en/conductor-introducing-context-driven-development-for-gemini-cli/), [KDnuggets (third-party)](https://www.kdnuggets.com/getting-started-with-conductor-for-gemini-cli)
  - ytstack today: durable artefacts in repo `.ytstack/` (intended committed) OR `~/.ytstack/projects/<basename-slug>/`; volatile `HANDOFF.md` written next to them by `hooks/pre-compact` (verified locally).

### Inferences
- Partition the artefacts: durable/planning (PROJECT.md, DECISIONS.md, STATE.md, milestone files) stay committed in `.ytstack/` (same model as GSD/Conductor); volatile (HANDOFF.md, journals, drafts, locks) move out-of-tree. Resolution order for the volatile root: `${CLAUDE_PLUGIN_DATA:-${PLUGIN_DATA:-}}` if set; else `${XDG_STATE_HOME:-$HOME/.local/state}/ytstack`. Using `~/.local/state` on macOS is defensible (spec default, no Apple guidance to the contrary, consistent with `~/.ytstack` already being a dotdir).
- Layout: `<root>/repos/<repo-key>/worktrees/<worktree-key>/sessions/<session_id>/{HANDOFF.md,journal.jsonl}` plus `<root>/repos/<repo-key>/latest-handoff -> sessions/<id>/HANDOFF.md` symlink updated atomically (`ln -sfn` into a temp name then `mv -f`). Keying by `session_id` removes the concurrent-writer problem entirely; journals become single-writer files and need no lock.
- Where a shared file is unavoidable (e.g. a per-repo index), keep each record under 512 bytes, write with a single `printf ... >> file` (shell `>>` opens O_APPEND), and guard with an `mkdir "$lock"` loop plus `trap 'rmdir "$lock"' EXIT` (bash 3.2 OK). Do not depend on `flock(1)` on macOS.
- Repo key: prefer `sha256(common-dir)` (A3) over remote-URL hashing; remote URL is absent for local-only repos and differs between ssh/https spellings. Basename slugs (`api`, `web`) collide across clients.
- Any `.ytstack/` write from a hook must first check `YT_IS_LINKED`; write to the worktree's own tree only if the artefact is meant to be committed on that branch; otherwise route to the state root. Add `.ytstack/HANDOFF.md` to `.gitignore` as transitional protection.

### Gaps
- No authoritative source for the macOS XDG mapping; it is convention, not spec.
- No measured data for Claude Code or Codex hook concurrency (two sessions firing PreCompact within the same millisecond); the single-writer-per-session design sidesteps measurement.

### Takeaway
Dependabot does not update or scan `ENV NODE_VERSION` lines (its Docker ecosystem handles image tags only and has no security updates for Docker at all); Renovate does, via a `customManagers` regex entry pointing at the `node-version` datasource with `versioning=node`. For scanning built images, Trivy does not identify a manually installed Node runtime (open proposal #10952), while Syft/Grype's `nodejs-binary` classifier does extract the version from the `node` binary and emits `cpe:2.3:a:nodejs:node.js` for CVE matching.

### Cited Findings
- Dependabot Docker ecosystem: version updates supported, **security updates "Not supported"**; "Dependabot parses Docker image tags for Semantic Versioning (SemVer)"; also updates image tags in Kubernetes manifests/Helm; nothing about `ENV`/`ARG` or arbitrary version strings; no custom datasource/regex mechanism. -- [Dependabot supported ecosystems](https://docs.github.com/en/code-security/dependabot/ecosystems-supported-by-dependabot/supported-ecosystems-and-repositories)
- Renovate regex custom manager: current keys `customType: "regex"`, `managerFilePatterns`, `matchStrings`, optional `datasourceTemplate`/`versioningTemplate`; the documented Dockerfile example uses an annotation comment `# renovate: datasource=github-tags depName=node packageName=nodejs/node versioning=node` above `ENV ..._VERSION=` lines, with `managerFilePatterns: ["/(^|/|\\.)Dockerfile$/", "/(^|/)Dockerfile\\.[^/]*$/"]`; "The syntax in the example is arbitrary, and you can set your own syntax"; RE2 engine (no backrefs/lookahead), matching is per-file not per-line. -- [Renovate regex manager](https://docs.renovatebot.com/modules/manager/regex/)
- Renovate `node-version` datasource: "returns NodeJS releases from nodejs.org API" (`https://nodejs.org/dist/index.json`), default versioning `node`. -- [Renovate node-version datasource](https://docs.renovatebot.com/modules/datasource/node-version/)
- Trivy: discussion #10952 (2026-07-11, open) "Detect manually installed Node.js runtimes and report Node.js core vulnerabilities": "Trivy does not currently identify the Node.js runtime version in container images" when Node is installed outside the OS package manager, including official `node` images; npm analyzers report package versions only; proposal to read `include/node/node_version.h` and ingest `nodejs/security-wg` core advisories; draft PRs trivy#10951 and trivy-db#683; no maintainer decision recorded. -- [aquasecurity/trivy discussion #10952](https://github.com/aquasecurity/trivy/discussions/10952). GitLab issue: "if a binary is manually downloaded/installed Trivy does not detect and scan it (we have seen examples for Node)". -- [gitlab-org/gitlab#461395](https://gitlab.com/gitlab-org/gitlab/-/issues/461395)
- Syft: `nodejs-binary` classifier matches a file path ending in `node`, extracts the version string from the binary, names the package `node.js` and maps CPE `cpe:2.3:a:nodejs:node.js` "so that NVD vulnerability matching works"; feature since Syft 0.60.1; duplicate entries when also installed via rpm acknowledged. -- [syft commit](https://github.com/anchore/syft/commit/edeba9c01c7a1181e4b06670c85db590a413967c), [Anchore blog](https://anchore.com/blog/detecting-binary-artifacts-with-syft/), [syft binary cataloger](https://pkg.go.dev/github.com/anchore/syft@v0.95.0/syft/pkg/cataloger/binary)
- Host-based detection alternatives: Akamai Guardicore queries enumerate running `node`/`nodejs`/`bun` processes and classify versions vulnerable/patched/EOL. -- [Akamai blog](https://www.akamai.com/blog/security-research/inside-node2shell-closer-look-cve-2026-111497)

### Inferences
- Minimal Renovate config for the Dockerfile pattern (keys per the regex-manager docs; the matchString is an inference assembled from the documented example, not a copy):

```json
{
  "customManagers": [
    {
      "customType": "regex",
      "description": "Bump curl-installed Node runtime pinned via ENV NODE_VERSION",
      "managerFilePatterns": ["/(^|/|\\.)Dockerfile$/", "/(^|/)Dockerfile\\.[^/]*$/"],
      "matchStrings": ["# renovate: datasource=node-version depName=node( versioning=(?<versioning>[a-z-]+))?\\s*\\nENV NODE_VERSION=(?<currentValue>\\S+)"],
      "datasourceTemplate": "node-version",
      "depNameTemplate": "node",
      "versioningTemplate": "{{#if versioning}}{{{versioning}}}{{else}}node{{/if}}"
    }
  ]
}
```
  with the Dockerfile line `# renovate: datasource=node-version depName=node` immediately above `ENV NODE_VERSION=24.22.2`. Pin by full version, not major, so the regex captures a comparable value.
- For image scanning, run Syft+Grype (or any scanner that uses Syft's binary classifier) in CI if the runtime is curl-installed; Trivy alone will miss the runtime CVE (it may still find npm package CVEs). A cheap belt-and-braces check is `docker run --rm <img> node -p process.version` compared against the nodejs.org index in CI.
- Dependabot users cannot cover this line; either switch the base to `FROM node:<version>` (Dependabot-updatable, Trivy-visible via image metadata is still not guaranteed per #10952) or add Renovate.

### Gaps
- Whether Grype currently matches CVE-2026-111497 against `cpe:2.3:a:nodejs:node.js` entries (the CVE is filed against Google Brotli, not Node.js, in KEV/GHSA) was not verified; NVD CPE configuration not readable.
- No verification that Renovate's RE2 accepts the exact matchString above; validate with `renovate-config-validator`.
