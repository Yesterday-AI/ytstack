# Agentic SDLC methodology and "development OS" frameworks: state of the art as of November 2026

Research date: 2026-11-07. Scope: spec-/plan-driven agentic dev frameworks, context-engineering consensus, multi-agent + eval practice, agent-state storage, brownfield bootstrapping, criticism of heavyweight methodology plugins. ytstack is deliberately NOT researched here; it is only the lens for "what is missing" in the Inferences sections. Anything sourced before roughly June 2026 is marked **(pre-mid-2026, possibly dated)**.

Source-quality note: GitHub star counts and release dates were read live from GitHub pages on 2026-11-07. Official Claude Code documentation (code.claude.com) was read live and is current. Several practitioner numbers (token percentages, benchmark hours) come from blogs and are flagged as unverified where that is the case.

## Key Question 1: Which spec-/plan-driven agentic dev frameworks are prominent in H2 2026 and what does each do?

### Takeaway
The field has consolidated into roughly three tiers: (a) very large, multi-harness spec-driven toolkits (GitHub Spec Kit ~148k stars, OpenSpec ~74k, GSD ~64k archived + ~11k successor, BMAD ~55k), (b) opinionated Claude-Code-first workflow plugins (Compound Engineering ~26k, Superpowers, Taskmaster), and (c) vendor-native spec systems (Kiro specs/steering, Google Conductor). Every surviving framework in 2026 (1) stores planning artifacts as committed Markdown in the repo, (2) runs heavy phases in fresh-context subagents, (3) is multi-harness (Claude Code, Codex, Cursor, Gemini CLI, OpenCode, ...), and (4) has added a "size the ceremony to the change" path (quick spec, bug-fix flow, build-only entry) during 2026.

### Cited Findings

**GSD (Get Shit Done) -> GSD Core**
- The original `gsd-build/get-shit-done` repo (64.2k stars, 5.4k forks, 2,928 commits) "was archived by the owner on Jun 26, 2026" and states "This repository is no longer the active home for GSD development"; development continues at `open-gsd/gsd-core` — [gsd-build/get-shit-done](https://github.com/gsd-build/get-shit-done)
- `open-gsd/gsd-core`: 11.3k stars, 815 forks, 6,532 commits on the `next` branch, MIT, npm `@opengsd/gsd-core` (`npx @opengsd/gsd-core@latest`), docs link "What's new in 1.7.0"; supports Claude Code, OpenCode, Antigravity CLI, Kimi CLI, Kilo, Codex, Copilot, Cursor, Windsurf — [open-gsd/gsd-core](https://github.com/open-gsd/gsd-core)
- Core loop per phase: Discuss (capture decisions before planning) → Plan (research, decompose, check the plan fits a fresh context window) → Execute (parallel waves, "Each executor starts with a clean 200k-token context") → Verify (walk through what was built, diagnose and fix before declaring phase done) → Ship (PR, archive phase) — [open-gsd/gsd-core README](https://github.com/open-gsd/gsd-core)
- Context-engineering rationale: "context rot" is treated as a property of attention over long sequences; the orchestrator "never edits source files. It spawns agents, collects their results, updates shared state, and routes to the next step". `/gsd-plan-phase` spawns a researcher (200k clean window), a planner and a plan-checker. `STATE.md` is read on startup and written after meaningful steps "so agents rely on the file rather than conversation memory". Since GSD 1.4.0 a context monitor uses `PreCompact`, `Stop`, `SubagentStop` and `FileChanged` hooks (FileChanged hot-reloads `config.json`). `context: fork` was REMOVED from the heavy skills (issue #921) "because those skills spawn subagents and a forked context lacks the Agent tool". Skills declare `effort: max` (plan/execute/autonomous) and `effort: low` (progress/stats) — [gsd-core docs/explanation/context-engineering.md](https://raw.githubusercontent.com/open-gsd/gsd-core/next/docs/explanation/context-engineering.md)
- Artifact model (`.planning/`): `PROJECT.md`, `ROADMAP.md`, `REQUIREMENTS.md` (numbered checkable IDs like `AUTH-01`), `STATE.md`, `config.json`, optional `MILESTONES.md`, `BACKLOG.md`, `LEARNINGS.md`, `DECISIONS-INDEX.md` ("rolling summary of prior CONTEXT.md decisions, generated when prior phases exceed the rolling-read threshold"), `METHODOLOGY.md`, transient `HANDOFF.json` ("written by /gsd-pause-work; consumed once by /gsd-resume-work"), `onboarding/SUMMARY.md`, `codebase/*.md`, `intel/API-SURFACE.md`. Per phase `phases/<NN>-<slug>/`: `<NN>-CONTEXT.md` (locked decisions with `D-NN` IDs), `<NN>-DISCUSSION-LOG.md`, `<NN>-RESEARCH.md`, `<NN>-VALIDATION.md`, `<NN>-PATTERNS.md`, `<NN>-<PP>-PLAN.md`, `<NN>-<PP>-SUMMARY.md`, `<NN>-VERIFICATION.md` (frontmatter `status: passed | gaps_found | human_needed`), `<NN>-UAT.md` (resumable across sessions), `.continue-here.md` (pause notes) — [gsd-core docs/reference/planning-artifacts.md](https://raw.githubusercontent.com/open-gsd/gsd-core/next/docs/reference/planning-artifacts.md)
- Planning commits are routed through a CLI (`gsd-tools query commit "docs(phase-03): ..." --files .planning/STATE.md`), which auto-skips when `commit_docs` is false or `.planning/` is gitignored; messages follow `docs(phase-NN): ...`, `docs: start milestone vX.Y`, `chore: remove phase NN` — [gsd-core references/git-planning-commit.md](https://cdn.jsdelivr.net/npm/@opengsd/gsd-core@1.4.4/gsd-core/references/git-planning-commit.md)
- Over 80 how-to guides exist, including `run-phases-autonomously.md`, `handle-quick-and-fast-tasks.md`, `batch-quick-tasks.md`, `set-up-cross-ai-review.md`, `enable-parallel-reviewer-lanes.md`, `work-in-parallel-with-workstreams.md`, `isolate-work-with-workspaces.md`, `keep-planning-docs-private.md`, `publish-prs-without-planning-artifacts.md`, `configure-model-profiles.md`, `drive-gsd-from-a-tracker-issue.md`, `enable-live-dom-verification.md` — [gsd-core docs tree](https://github.com/open-gsd/gsd-core/tree/next/docs)

### Inferences
- Consensus artifact model in 2026: a small set of root files (project/product, requirements or constitution, roadmap/tracks, state) plus one folder per unit of work containing spec/plan/tasks/summary/verification, all committed. The unit of work has a verification artifact with a machine-readable status (GSD `status: passed|gaps_found|human_needed`, Anthropic `passes: true/false`, Kiro task checkboxes).
- "Fresh context per heavy phase" is now the default execution model everywhere (GSD executors at 200k, Compound Engineering reviewers, Superpowers review subagents, Kiro waves). The orchestrator stays thin and does not edit source files.
- Every major framework became multi-harness during 2026 (GSD, BMAD, Superpowers 6, Compound Engineering, OpenSpec, Spec Kit). A plugin that only targets Claude Code is now the minority position.
- Every framework added a lightweight path in 2026: Kiro Quick Spec (no gates), BMAD "two-section spec, one session", Spec Kit bug-fix extension, GSD quick/batch tasks, OpenSpec `/opsx:ff`. Mandatory multi-gate planning for every change is no longer state of the art.
- Requirement IDs that are checkable (`AUTH-01`, `D-NN`) and index/rollup files for append-only logs (GSD `DECISIONS-INDEX.md`) are the practical answers to append-only decision logs that grow past what a session should read.

### Gaps
- GSD Core "fits one context window" numeric limits (tasks per plan, token ceiling) are not published on the pages read; only "check that the plan fits a fresh context window" and "200k-token" executor windows are stated.
- Spec Kit's official "existing projects" guide and the definition of "Living Specs"/"converge" could not be fetched (404 on the guessed URL); only the README news links confirm their existence (Oct 2026).
- BMAD v7 contents beyond "skills-based preview" and the 14→8 skill reduction are not documented on the pages read.
- No release dates with year appear on GitHub release pages for Spec Kit/BMAD (day-month only); the year is inferred from context (page read 2026-11-07, latest entries "06 Nov").

## Key Question 2: Context-engineering consensus in 2026 (progressive disclosure, just-in-time context, skill description budgets, inject vs reference, memory tools, CLAUDE.md vs AGENTS.md, SessionStart injection size)

### Takeaway
The consensus is codified in official Claude Code docs: CLAUDE.md under ~200 lines, skills under 500 lines with one-level-deep references, per-skill description capped at 1,536 chars inside a listing budget of 1% of the context window, SessionStart `additionalContext` capped at 10,000 chars (overflow is spilled to a file Claude is not told to read), and auto memory loaded as only the first 200 lines / 25 KB of a `MEMORY.md` index. AGENTS.md is now a Linux Foundation (AAIF) standard that Claude Code reads natively since v2.1.277, and Codex caps the merged AGENTS.md chain at 32 KiB.

### Cited Findings
- **(pre-mid-2026, possibly dated)** Anthropic's context-engineering post (Sep 29, 2025): goal is "the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome"; agents should "maintain lightweight identifiers (file paths, stored queries, web links, etc.)" and load just-in-time; Claude Code is cited as the hybrid: CLAUDE.md dropped in up front, glob/grep for just-in-time retrieval; compaction should "start by maximizing recall"; "One of the safest lightest touch forms of compaction is tool result clearing"; structured note-taking (e.g. "maintaining a NOTES.md file"); sub-agents "return only a condensed, distilled summary of its work", often 1,000–2,000 tokens; "do the simplest thing that works" — [Anthropic engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- CLAUDE.md: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence"; `@imports` "help you organize a long file but don't reduce its context cost"; move part-of-codebase rules to `.claude/rules/` (path-scoped, load only for matching files); "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook"; `/doctor prompt-audit` (v2.1.283+) finds outdated/conflicting instructions across CLAUDE.md, AGENTS.md, rules, skills, agents — [code.claude.com memory](https://code.claude.com/docs/en/memory)
- Auto memory: per-repo directory `~/.claude/projects/<project>/memory/` with a `MEMORY.md` index ("one line per memory, loaded into every session") plus topic files; only "first 200 lines or 25KB" of MEMORY.md loads; "all worktrees and subdirectories within the same repo share one auto memory directory"; machine-local, not shared across machines; four note types recorded as frontmatter `type`; `autoMemoryDirectory` setting; `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` — [code.claude.com memory](https://code.claude.com/docs/en/memory)
- AGENTS.md in Claude Code: "Reading AGENTS.md directly requires Claude Code v2.1.277 or later"; default `claude-md-or-agents-md` reads AGENTS.md only when no CLAUDE.md/CLAUDE.local.md exists in cwd or above; `claude-md-and-agents-md` loads both (via `pluginConfigs` → `cc-plugin-agents-md@builtin`, v2.1.285+); "A SessionStart hook that prints AGENTS.md: remove it. Once Claude reads AGENTS.md directly, the hook adds a second copy"; a `CLAUDE.md` symlinked to `AGENTS.md` is fine but Edit/Write "refuse to write through a symlink" and Windows checkouts need `core.symlinks`; `InstructionsLoaded` hooks don't fire for an AGENTS.md read via the setting — [code.claude.com memory](https://code.claude.com/docs/en/memory)
- `/init` with `CLAUDE_CODE_NEW_INIT=1` is a multi-phase flow that asks which artifacts to set up (CLAUDE.md, skills, hooks) and imports `AGENTS.md`, `.devin/rules/`, `.windsurf/rules/`, `.clinerules`; `/import` copies another agent's config — [code.claude.com memory](https://code.claude.com/docs/en/memory)
- agents.md standard: "now stewarded by the Agentic AI Foundation (AAIF) under the Linux Foundation"; used in "over 60,000 open-source projects"; supporters listed: Codex, Jules, Factory, Aider, goose, opencode, Zed, Warp, VS Code, Devin, UiPath, Junie, Amp, Cursor, RooCode, Gemini CLI, Kilo Code, Phoenix, Semgrep, GitHub Copilot coding agent, Ona, Windsurf, Augment Code (Claude Code not listed on the site despite native support); nesting: "the AGENTS.md closest to the edited file wins"; openai/codex has 88 such files — [agents.md](https://agents.md/)
- Codex: reads `AGENTS.override.md` then `AGENTS.md` at `~/.codex` and in each directory from project root down to cwd, "at most one file per directory", concatenated root→cwd; `project_doc_max_bytes` defaults to 32 KiB and "loading stops once the combined size reaches the limit"; `project_doc_fallback_filenames` config; recommends a `## Code Review Rules` section and "concise rules" — [OpenAI Codex AGENTS.md guide](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
- Empirical study: 466 OSS projects with AI context files; "no established content structure yet"; content classified as descriptive, prescriptive, prohibitive, explanatory, conditional; MSR 2026 paper, v4 revised Feb 5, 2026 — [arXiv 2510.21413](https://arxiv.org/abs/2510.21413)
- Skills (Claude Code): combined `description` + `when_to_use` "truncated at 1,536 characters" per skill (`skillListingMaxDescChars`); the whole listing's budget "scales at 1% of the model's context window" (`skillListingBudgetFraction`, or `SLASH_COMMAND_TOOL_CHAR_BUDGET` as fixed chars); on overflow "Claude Code drops descriptions starting with the skills you invoke least"; `/doctor` estimates listing cost; `/skill-doctor` finds unused skills; `skillOverrides` can set entries to `"name-only"`; after compaction "Claude Code can keep only the start of an invoked skill, so put the most important instructions near the top of SKILL.md"; "Once a skill loads, its content stays in context across turns, so every line is a recurring token cost"; keep SKILL.md under 500 lines; skills support `paths`, `context: fork`, `disable-model-invocation`, `effort`, `model`, `hooks` frontmatter — [code.claude.com skills](https://code.claude.com/docs/en/skills)
- Skill authoring (platform docs): `name` ≤64 chars, `description` ≤1,024 chars, third person; "Keep the SKILL.md body under 500 lines"; "Keep references one level deep from SKILL.md" (Claude may `head -100` nested references); TOC for reference files >100 lines; "Default assumption: Claude is already very smart"; degrees-of-freedom guidance (high/medium/low); "Avoid offering too many options"; test with Haiku, Sonnet and Opus — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Hooks: SessionStart matchers `startup`, `resume`, `clear`, `compact`, `fork`; context is injected via plain stdout or `hookSpecificOutput.additionalContext`, wrapped "in a system reminder ... at the start of the conversation"; docs recommend "phrasing it as factual statements, because imperative, system-style wording can trigger prompt-injection defenses"; general limit of "10,000 characters" per string; above it Claude Code "saves it to a file in the session directory ... gives Claude the file path and a preview of the first 2,000 characters" but "doesn't ask Claude to read the file"; `mcp_tool` hooks on SessionStart at launch are skipped; `PreCompact` and `PostCompact` both exist; 34 events in total — [code.claude.com hooks](https://code.claude.com/docs/en/hooks)
- Subagents start with "a fresh, isolated context window"; they DO receive the CLAUDE.md hierarchy (user, project, local, managed, AGENTS.md) except Explore/Plan; they do NOT inherit conversation history, invoked skills, files read, output style or auto memory; "If a rule must reach a subagent, restate it in the delegation prompt"; subagent `memory:` scope `user` (`~/.claude/agent-memory/<name>/`), `project` (`.claude/agent-memory/<name>/`, "can be committed"), `local` (`.claude/agent-memory-local/<name>/`); `project` is the recommended default; first 200 lines / 25KB of its MEMORY.md are loaded — [code.claude.com sub-agents](https://code.claude.com/docs/en/sub-agents)
- Memory tool (API): client-side `/memories` file ops; the API auto-adds a system prompt: "ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE ... ASSUME INTERRUPTION: Your context window might be reset at any moment"; pairs with context editing and server-side compaction ("compaction keeps the active context small... memory preserves the information that must survive summarization") — [platform.claude.com memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Best practices on context cost: "With a 1M-token window on most current models and compaction near the top of it, you'll rarely run out of context. You can still pay for context you don't need"; `/usage` breaks usage down "by skill, subagent, plugin, and MCP server"; `/clear` between unrelated tasks; `/compact` with a focus; Skills are "lighter on context than CLAUDE.md" for procedures because only name+description is always loaded — [code.claude.com best-practices](https://code.claude.com/docs/en/best-practices)
- Third-party measurement **(pre-mid-2026, possibly dated)**: Scott Spence's sandboxed evals (Feb 8, 2026; 22 prompts x 5 hook configs x 2 runs, Sonnet 4.5) found baseline skill auto-activation of 50–55%, a "forced-eval" UserPromptSubmit hook at 100%, native `type: prompt` hook no better than none; "Whenever Claude activated a skill, it picked the correct one. The problem is activation, not selection" — [scottspence.com](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals)

### Inferences
- The modern split is: CLAUDE.md/AGENTS.md = always-loaded facts (<200 lines), `.claude/rules/` = path-scoped facts, skills = procedures loaded on demand, hooks = rules that cannot have exceptions. Long "using-X" skills that re-explain methodology at session start contradict the "only what Claude can't find on its own" rule.
- A SessionStart hook that injects state must stay under 10,000 characters and be worded as facts, not instructions; anything larger silently degrades into a file path plus 2,000-char preview. Injecting whole STATE.md/HANDOFF.md/recent summaries concatenated is exactly the pattern this limit breaks.
- With native AGENTS.md support, the "AGENTS.md canonical + CLAUDE.md symlink" pattern is officially endorsed but the symlink causes Edit refusals and Windows breakage; the `@AGENTS.md` import is the safer cross-platform variant.
- Skill-description budgets are a real constraint for plugins with 20+ skills: 1% of a 200k-token window is ~2,000 tokens, roughly 8,000 characters, and per-skill text is capped at 1,536 chars, so about 5–6 maximal descriptions fill the budget before least-used skills lose their descriptions (and thus auto-activation); on a 1M window the budget is ~5x larger. Front-loading the key trigger terms and using `skillOverrides: name-only` for rarely used skills is the documented mitigation. (The token/char conversion is my estimate; the docs give the rule, not the arithmetic.)
- Auto memory and subagent `memory: project` provide a built-in, index-first knowledge store with a 200-line/25KB loading cap; a framework-level KNOWLEDGE.md now overlaps with it and should either feed it or be shaped like it (one-line index + topic files).

### Gaps
- Anthropic has not published an official recommended size specifically for SessionStart context; only the 10,000-character hard limit per string and the auto-memory 200-line/25KB rule are documented.
- The exact context-window size used for the 1% skill-listing budget per model is not stated on the page read; the arithmetic above is an estimate.
- No official Anthropic engineering post on "agent memory" from 2026 was found; the memory guidance comes from product docs (memory tool, auto memory) rather than a dated essay.

## Key Question 3: Multi-agent patterns (orchestrator-worker, worktree-per-agent, fresh context per task, verifier/critic agents) and evals for skills and hooks

### Takeaway
Official guidance now ranks parallelism options: subagents first, cross-session messaging second, Agent Teams last ("check whether a lighter option does the job"); Agent Teams remain experimental, flag-gated, cannot be resumed, and cannot nest. Worktree isolation is built into Claude Code for sessions (`--worktree`) and subagents (`isolation: worktree`), with hard enforcement against edits to the main checkout. For evals, `claude plugin eval` (v2.1.269+, Sept 2026) is the standard: 3 runs per case, with/without-plugin ablation, six grader types, CI exit codes, and the skill-creator plugin covers single-skill iteration; frameworks like Superpowers publish eval repos with planted-defect gates.

### Cited Findings
- Agent teams: "experimental and disabled by default", `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`; "Before you set up a team, check whether a lighter option does the job. Subagents work within a single session, and with cross-session messaging Claude can pass findings between the sessions you run yourself"; teammates load CLAUDE.md, MCP servers and skills but "The lead's conversation history does not carry over"; shared task list with file locking and dependency blocking; mailbox at `~/.claude/teams/{team-name}/inboxes/`, tasks at `~/.claude/tasks/{team-name}/`; quality gates via `TeammateIdle`, `TaskCreated`, `TaskCompleted` hooks (exit 2 blocks and sends feedback); plan approval: a teammate spawned while lead is in plan mode sends a plan approval request that "Claude Code approves ... as soon as the request arrives, without the lead reviewing it" unless the teammate's mode was changed; "Start with 3-5 teammates"; "Having 5-6 tasks per teammate keeps everyone productive"; limitations: "No session resumption with in-process teammates", "Task status can lag", "One team per session", "No nested teams", "No background subagents from in-process teammates", "Lead is fixed"; "Agent teams use significantly more tokens than a single session" — [code.claude.com agent-teams](https://code.claude.com/docs/en/agent-teams)
- Worktrees: `claude --worktree <name>` creates `.claude/worktrees/<name>/` on branch `worktree-<name>`; tip: "Add `.claude/worktrees/` to your .gitignore"; `.worktreeinclude` (gitignore syntax) copies gitignored files such as `.env` into every new worktree; subagent `isolation: worktree` branches "from your repository's default branch unless `worktree.baseRef` is set to `"head"`"; isolation is enforced: Edit/Write to the main checkout are blocked, Bash commands whose cwd resolves to the main checkout are blocked, git redirects (`git -C`, `GIT_DIR`) are blocked; "Hook paths don't follow the worktree": `${CLAUDE_PROJECT_DIR}` stays at the original root, hooks must read `cwd` from the input JSON; a subagent in its own worktree "doesn't load the CLAUDE.md file or .claude/rules/ directory at the worktree's root"; permission approvals from a worktree session are saved "to the main checkout's `.claude/settings.local.json`" and apply to every worktree; a periodic sweep removes agent worktrees older than `cleanupPeriodDays` unless they hold work; `git worktree lock` is held while an agent runs — [code.claude.com worktrees](https://code.claude.com/docs/en/worktrees)
- Subagents: "Use a subagent when: The task produces verbose output you won't need again... The work is self-contained and can return a summary... You want to enforce tool restrictions, for example a read-only reviewer"; a cold subagent "can end up slower" because it must regather context; `autoCompactWindow` frontmatter (v2.1.296+); fork subagents inherit the parent conversation and tool pool; background subagents get a smaller tool set — [code.claude.com sub-agents](https://code.claude.com/docs/en/sub-agents); [best-practices](https://code.claude.com/docs/en/best-practices)
- Verifier/critic: `/code-review` "reviews the diff in a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code"; example prompt "use a subagent to review the rate limiter diff against SPEC.md, check every requirement is implemented and the listed edge cases have tests"; `/verify` runs the app; a read-only reviewer is enforced via `tools: Read, Grep, Glob` "by Claude Code rather than requested in a prompt" — [code.claude.com best-practices](https://code.claude.com/docs/en/best-practices)
- GSD Core: orchestrator spawns researcher/planner/plan-checker; executors run in parallel waves with clean 200k contexts; verify step generates fix plans; how-tos for "parallel reviewer lanes", "cross-AI review", "workstreams", "workspaces" — [gsd-core README](https://github.com/open-gsd/gsd-core); [docs tree](https://github.com/open-gsd/gsd-core/tree/next/docs)
- Kiro: all-tasks execution builds a dependency graph and runs independent tasks "in waves ... concurrently" — [kiro.dev/docs/specs](https://kiro.dev/docs/specs/)
- Third-party handbook estimate **(unverified)**: Agent Teams ≈ 7× tokens vs a single session; "Token cost scales linearly per teammate; coordination overhead grows superlinearly" — [knowledgebase-862 handbook](https://knowledgebase-862.pages.dev/r/claude-agent-teams)
- `claude plugin eval`: requires "Claude Code v2.1.269 or later"; suite lives in `evals/<case>/{prompt.md, case.yaml, graders/<name>.md}`; `claude plugin eval init` has Claude propose cases and graders; "each case runs three times by default"; six grader types including `regex`, `tool_used`, `tool_order`, `llm`, `baseline` ("There are no custom-code graders"); default runs a with-arm and a without-arm (no-plugin baseline) and reports `WITH`, `W/OUT`, `Δ`, `COST`; graders like `tool_used: Skill` are auto-excluded from the baseline arm (`scored: false`) to keep arms comparable; `--ablation none` halves cost; `--threshold` (default `1.0`) gates exit code 1; `--json`, `--max-cost-usd` (exit 2 = partial), `--judge-model`, `--trust-plugin` for CI; mock MCP servers via `evals/mocks/<server>/<tool>.md`; `context.scaffold_script` seeds fixture repos; `context.history_file` continues a transcript; `report.html` is self-contained; "The most common first finding is a Δ near zero with the case's `tool_used: Skill` grader failing, which means Claude isn't choosing your skill on natural phrasing. Adjust the skill's description"; stability advice: regex over produced files for long output, llm graders only for short output with concrete PASS/FAIL rubrics; "To check that a build or test passed inside the run, have the prompt ask Claude to run it and write the outcome to a file, grade that file, and assert the command ran with a `tool_used` grader" — [code.claude.com plugin-evals](https://code.claude.com/docs/en/plugin-evals)
- skill-creator plugin: `evals/evals.json` inside the skill; runs each case "in an isolated subagent, with and without the skill"; writes `grading.json`, `benchmark.json` (pass rate, time, tokens with vs without); blind A/B between two skill versions; "Description tuning: generates should-trigger and should-not-trigger prompts, measures the hit rate, and proposes description edits"; HTML review viewer; formats of skill-creator and `claude plugin eval` are not interchangeable — [code.claude.com skills](https://code.claude.com/docs/en/skills)
- `claude plugin validate <dir>` checks SKILL.md frontmatter/schema (v2.1.233+) — [code.claude.com skills](https://code.claude.com/docs/en/skills)
- Platform skill guidance: "Create evaluations BEFORE writing extensive documentation"; "Build three scenarios that test these gaps"; establish a no-skill baseline; eval JSON with `skills`, `query`, `files`, `expected_behavior` — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Superpowers 6 eval practice: public `superpowers-evals` repo, `superpowers-autoresearch` loop with "pre-registered hypotheses" and "planted-defect gates ... for review quality"; a Codex eval run initially showed no improvement because "the evals were not isolated from the host and were actually benchmarking Superpowers 5.1.0" — [blog.fsck.com Superpowers 6](https://blog.fsck.com/2026/06/15/Superpowers-6/)
- Hook testing practice (community): pipe sample JSON into the hook script and assert on exit code 2 specifically (exit 1 is non-blocking); `claude --debug` and `/hooks` to verify registration; Stop hooks guard against loops via `stop_hook_active` — [blakecrosley.com hooks explained](https://blakecrosley.com/blog/claude-code-hooks-explained); [dev.to deterministic hooks](https://dev.to/gentic_news/stop-relying-on-claudemd-for-guarantees-build-deterministic-hooks-instead-35kp)

### Inferences
- The 2026 default for parallel execution is "orchestrator + fresh subagents in isolated worktrees", not Agent Teams. Teams buy inter-agent discussion (debate, review) at a steep token cost and lose resumability; the docs steer implementation parallelism toward subagents with `isolation: worktree` and file-ownership partitioning.
- Verification is being moved from prose ("run verification before claiming done") into harness mechanisms: Stop hooks (exit 2), `TaskCompleted` hooks for teams, read-only reviewer subagents enforced by `tools:`, and machine-readable pass/fail files graded by regex. A skill that merely instructs "verify first" is now considered the weak form.
- Evals are expected to ship with the plugin: a `evals/` directory with `tool_used: Skill` activation cases plus one outcome grader per case, run in CI with `--json --threshold`. Frameworks without published evals (and without a with/without delta) cannot claim their ceremony pays for itself; Superpowers' own data shows parts of its ceremony were marginal.
- Hook paths and project config do not follow worktrees (`${CLAUDE_PROJECT_DIR}` fixed, subagent worktrees skip the worktree's CLAUDE.md), so any hook that writes state must derive the target path from the hook input `cwd`, not from the project dir, or it will write handoffs/journals into the main checkout from inside a worktree.

### Gaps
- No official Anthropic documentation on a dedicated test harness for hooks was found; hook testing guidance is community-level (pipe JSON, assert exit codes).
- The ~7× token multiplier for Agent Teams is a third-party estimate; Anthropic's cost page was not fetched.
- No independent benchmark comparing orchestrator+subagents versus Agent Teams on the same implementation task was found.

## Key Question 4: Where practitioners put agent-runtime state (handoffs, journals, drafts) and reported problems with dirty working trees / shared checkouts

### Takeaway
Planning artifacts (plans, specs, summaries, state) are committed in-repo by default in every major framework (GSD `.planning/`, Spec Kit `.specify/`, OpenSpec `openspec/`, Conductor `conductor/`, Compound Engineering `docs/plans|solutions`), with explicit mechanisms to keep them out of PRs (GSD `/gsd-pr-branch` strict mode, OpenSpec "Stores" in a separate repo). Transient runtime state (pause handoffs, team mailboxes, task lists, auto memory) lives outside the tree or as a single consume-once file. The documented failure mode of gitignoring planning dirs is partial tracking (already-tracked files keep committing while new ones vanish); the documented fix for shared checkouts is worktrees plus `.worktreeinclude`, with caveats that permission approvals and auto memory are shared across worktrees while `CLAUDE.local.md` is not.

### Cited Findings
- GSD: `commit_docs` defaults to true; "if `.planning/` is gitignored, `commit_docs` is automatically `false` regardless of config.json"; local-only setup requires `commit_docs false` + `.gitignore` + `git rm -r --cached` for already-tracked files — [learnship planning artifacts](https://faviovazquez.github.io/learnship/core-concepts/planning-artifacts); [gsd git settings](https://www.mintlify.com/gsd-build/get-shit-done/reference/git-settings)
- GSD `/gsd-pr-branch`: keeps `.planning/` versioned on the working branch "so parallel executors can read their plans and `/gsd-undo` can restore earlier states", then "creates a `<your-branch>-pr` branch from the target branch and rebuilds your commits without any `.planning/` path"; `planning.pr_strict true` removes every `.planning/` path including `STATE.md` and `ROADMAP.md`; verify with `git diff --name-only main..<branch>-pr | grep '^\.planning/'`; tradeoff: "The working branch still contains planning history, so it must never be pushed"; keeping planning out of git entirely "loses worktree isolation" — [gsd-core how-to publish-prs-without-planning-artifacts](https://raw.githubusercontent.com/open-gsd/gsd-core/next/docs/how-to/publish-prs-without-planning-artifacts.md)
- GSD transient state: `HANDOFF.json` is "Machine-readable resume point ... Written by /gsd-pause-work; consumed once by /gsd-resume-work"; `.continue-here.md` per phase holds pause instructions and is "checked on entry to discuss-phase and plan-phase" — [gsd-core planning-artifacts](https://raw.githubusercontent.com/open-gsd/gsd-core/next/docs/reference/planning-artifacts.md)
- Real-world incident: a project (HanSur94/FastSense) gitignored `.planning/`, `.superpowers/`, `docs/superpowers/`; because "git only ignores untracked files", 75 already-tracked `.planning` files kept being committed while 409 newer planning docs (~6.8 MB) "never entered the repo"; PR #168 (merged May 29, 2026) removed the ignore rules and committed the hidden docs, keeping only `.superpowers/` (brainstorm scratch) ignored — [FastSense PR #168](https://github.com/HanSur94/FastSense/pull/168)
- Compound Engineering: plans in `docs/plans/`, learnings in `docs/solutions/`, movable under one root with `docs_root` "when `docs/` holds tracked content"; config in `.compound-engineering/config.yaml` — [EveryInc/compound-engineering-plugin](https://github.com/EveryInc/compound-engineering-plugin)
- Conductor: context is "a managed artifact alongside your code"; `/conductor:conductor-revert` works through git history on tracks/phases/tasks, implying committed artifacts — [gemini-cli-extensions/conductor](https://github.com/gemini-cli-extensions/conductor)
- OpenSpec: `openspec/` in-repo; archived changes under `openspec/changes/archive/<date>-<name>/`; "Stores (beta): a way to keep planning in a separate shared repo for cross-repo features" — [Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec)
- BMAD v6.11: stops storing derived documentation; `bmad-project-context` writes "one verified block in the repository's AGENTS.md" and "anything derivable from source is read live rather than stored" — [BMAD releases](https://github.com/bmad-code-org/BMAD-METHOD/releases)
- Claude Code runtime state outside the repo: auto memory in `~/.claude/projects/<project>/memory/` (shared by all worktrees of a repo, excluded from the transcript retention sweep); agent-team config in `~/.claude/teams/` (removed at session end) and task lists in `~/.claude/tasks/` (kept until `cleanupPeriodDays`); "There is no project-level equivalent of the team config. A file like `.claude/teams/teams.json` in your project directory is not recognized" — [memory](https://code.claude.com/docs/en/memory); [agent-teams](https://code.claude.com/docs/en/agent-teams)
- Claude Code committable vs local: subagent `memory: project` → `.claude/agent-memory/<name>/` ("can be committed"); `memory: local` → `.claude/agent-memory-local/<name>/` ("shouldn't be checked in"); `CLAUDE.local.md` is gitignored and "only exists in the worktree where you created it" — the documented workaround is `@~/.claude/my-project-instructions.md` — [sub-agents](https://code.claude.com/docs/en/sub-agents); [memory](https://code.claude.com/docs/en/memory)
- Shared-checkout leakage via worktrees: permission approvals from a worktree session are saved to the main checkout's `.claude/settings.local.json` and apply to every worktree; project-scope plugins load in all worktrees; untracked `.claude/skills|agents|commands` read through from the main checkout when the worktree lacks them (v2.1.277+) — [worktrees](https://code.claude.com/docs/en/worktrees)
- Hooks and worktrees: `${CLAUDE_PROJECT_DIR}` "still points at the project root where the session started"; the hook input `cwd` "is the worktree root, and it moves again when Claude runs `cd`"; desktop-app worktree sessions read hooks/settings/skills from the main checkout root while CLAUDE.md and rules load from the worktree — [worktrees](https://code.claude.com/docs/en/worktrees)
- Worktree cleanup: on exit, a dirty worktree ("changed or untracked files, uncommitted work inside checked-out submodules, and new commits") prompts Keep or Remove; `-p` runs never clean up; a periodic sweep removes agent worktrees older than `cleanupPeriodDays` only if they hold no work; `WorktreeRemove` hooks cannot block deletion (third-party claim) — [worktrees](https://code.claude.com/docs/en/worktrees); [felixschmidt.software](https://felixschmidt.software/en/blog/claude-code-worktrees-2026)
- Anthropic long-running-agent pattern **(pre-mid-2026, possibly dated)**: `claude-progress.txt` + feature-list JSON + git commits as the recovery substrate; JSON chosen because agents are less likely to overwrite it than Markdown — [Anthropic engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Handoff tooling (community, mostly mid-2026): a `SESSION-HANDOFF.md` per project that CLAUDE.md mandates updating "before every session end or context compaction", printed by a SessionStart hook — [dev.to devforgedev](https://dev.to/devforgedev/the-one-file-that-makes-claude-code-sessions-actually-persistent-48n2); pi's handoff extension argues "compaction loses information" and writes a structured document (decisions, files, next steps) that the user reviews before a new session is seeded — [pi-handoff](https://pi.dev/packages/@jackice/pi-handoff); `session-handover` (PyPI) adds a SessionEnd hook that "extracts unfinished tasks, decisions, and follow-ups from the transcript tail" and separately "audits what /compact drops" — [session-handover 0.5.0](https://pypi.org/project/session-handover/0.5.0/)
- Kiro Web: "On Web, PR feedback from the task creator teaches the agent" (state learned from review, not from repo files) — [kiro.dev/docs/steering](https://kiro.dev/docs/steering/)

### Inferences
- The field's answer to "committed vs gitignored" is: commit durable planning artifacts (they are the audit trail and the only thing worktrees/executors can share), keep transient runtime state (handoff JSON, team inboxes, scratch) either out of the repo or as a single consume-once file, and solve PR hygiene with a filter branch or a separate planning repo rather than with `.gitignore`.
- Hooks that write journals/handoffs on `PreCompact`/`SessionEnd` into the repo create a dirty tree by construction. Frameworks avoid this either by committing those writes via a CLI with a `docs(...)` message (GSD), or by writing to a user-dir location (Claude Code's own auto memory, teams, tasks). A journal that is neither committed nor ignored is the worst of both.
- For parallel sessions on one checkout, the ecosystem has given up on "share one working tree" and standardized on worktrees; the remaining shared surfaces (settings.local.json approvals, auto memory, plugins) are shared by design. Per-worktree personal instructions need the home-dir import trick.
- Consume-once handoffs (GSD `HANDOFF.json`) are cleaner than an ever-growing `HANDOFF.md`: the file disappears after resume, so stale handoffs cannot mislead a later session.

### Gaps
- I found no systematic study of "agent hooks dirty the working tree"; evidence is one documented PR (FastSense #168) plus GSD's design docs. No Anthropic guidance on committing vs ignoring hook-written files was found.
- Spec Kit's and BMAD's official stance on gitignoring `.specify/` / `_bmad/` was not found in the pages read.

## Key Question 5: Brownfield adoption: how frameworks bootstrap from existing README/docs/ADRs instead of a greenfield pitch

### Takeaway
Every major framework now has a dedicated brownfield entry: GSD `/gsd-onboard` → `/gsd-map-codebase` (four parallel mapper agents producing seven `codebase/*.md` files, detection of ADRs/PRDs triggers a docs-ingest step), BMAD `bmad-project-context` (a single verified block in AGENTS.md, derived facts read live), OpenSpec `/opsx:onboard`, Kiro "Generate Steering Docs" (product/tech/structure), Spec Kit `specify init --here` plus community constitution-from-codebase and brownfield extensions, Conductor "intelligent initialization" for brownfield. The shared rule: describe the codebase as it is, anchor the tech stack as established fact, and put new-work requirements (not existing behaviour) into the requirements file.

### Cited Findings
- GSD `/gsd-onboard` "checks the repo state and prints the next safe command. If code exists and `.planning/codebase/` is missing, it tells you to map the codebase first... If it detects ADRs, PRDs, specs, RFCs, or requirements docs, it recommends a docs-ingest handoff first." `/gsd-map-codebase` runs four parallel mapper agents (Tech, Architecture, Quality, Concerns) in "1–5 minutes", producing `.planning/codebase/STACK.md`, `ARCHITECTURE.md`, `STRUCTURE.md`, `CONVENTIONS.md`, `TESTING.md`, `INTEGRATIONS.md`, `CONCERNS.md`. `/gsd-new-project` then "recognizes the repo as brownfield and asks about what you are adding, not what already exists", writes `PROJECT.md` with existing capabilities in a **Validated** section, and `REQUIREMENTS.md` holds only the new feature's requirements; a roadmapper proposes one phase for a small change; `.planning/onboarding/SUMMARY.md` indexes the setup — [gsd-core tutorial onboarding-an-existing-codebase](https://raw.githubusercontent.com/open-gsd/gsd-core/next/docs/tutorials/onboarding-an-existing-codebase.md)
- BMAD: "Existing codebases: Consider running `bmad-project-context`, then build as usual"; since v6.11.0 that skill replaces generated documentation with "one verified block in the repository's AGENTS.md"; "An existing project-context.md still loads as a source" — [docs.bmad-method.org](https://docs.bmad-method.org/); [BMAD releases](https://github.com/bmad-code-org/BMAD-METHOD/releases)
- Kiro: the IDE's "Generate Steering Docs" creates `product.md`, `tech.md`, `structure.md`; enterprise page: "Bring existing architecture docs, diagrams, or code. Kiro infers requirements and generates a structured plan"; third-party guidance: "steering rules must describe the existing architecture, not an ideal one" — [kiro.dev/docs/steering](https://kiro.dev/docs/steering/); [kiro.dev/enterprise](https://kiro.dev/enterprise/); [Kiro methodology (third party)](https://d3epcbk5uvoo5c.cloudfront.net/10-workflow-existing-code.html)
- OpenSpec: "built for brownfield not just greenfield"; `/opsx:onboard` in the expanded profile; delta specs (`## ADDED Requirements`) describe changes against existing specs rather than restating the system — [Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec)
- Spec Kit: README links an "Existing projects" guide; the community `spec-kit-brownfield` extension adds `/speckit.brownfield.bootstrap` (generate configuration from the codebase) and `/speckit.brownfield.migrate` (adopt SDD incrementally with reverse-engineered specs); issue #1436 argues "the brownfield project tech stack is established fact, so the constitution must anchor it, and that existing architecture should be documented rather than 'improved'"; a fork offers `/speckit.discover-constitution` to derive a constitution from existing patterns and `specify init --here` — [spec-kit README](https://github.com/github/spec-kit); [speckit-community brownfield extension](https://speckit-community.github.io/extensions/brownfield); [spec-kit issue #1436](https://github.com/github/spec-kit/issues/1436); [markhazleton fork](https://markhazleton.github.io/spec-kit/quickstart.html)
- Conductor: "supports both new (Greenfield) and existing (Brownfield) projects with 'intelligent initialization'" (mechanism not described) — [gemini-cli-extensions/conductor](https://github.com/gemini-cli-extensions/conductor)
- Claude Code `/init`: "Claude analyzes your codebase and creates a file with build commands, test instructions, and project conventions it discovers. If a CLAUDE.md already exists, `/init` suggests improvements"; with `CLAUDE_CODE_NEW_INIT=1` it asks which artifacts to set up (CLAUDE.md, skills, hooks) and imports existing AGENTS.md / `.windsurf/rules/` / `.clinerules` — [code.claude.com memory](https://code.claude.com/docs/en/memory)
- Compound Engineering: `/ce-setup` works "in any project"; `docs_root` exists to relocate artifact folders "when `docs/` holds tracked content" (brownfield collision avoidance) — [EveryInc/compound-engineering-plugin](https://github.com/EveryInc/compound-engineering-plugin)
- Third-party comparison **(unverified, vendor blog)**: OpenSpec's delta tracking "suits brownfield iteration better" while Kiro's "center of gravity is greenfield to production" — [codemyspec Kiro vs OpenSpec](https://codemyspec.com/blog/kiro-vs-openspec)

### Inferences
- The brownfield entry point is a codebase map step, not a pitch. Frameworks spawn parallel read-only mappers, write a handful of descriptive files (stack, architecture, conventions, testing, concerns), and then treat existing capabilities as already validated so the first milestone is scoped to the delta.
- Existing ADRs/PRDs/README are ingested (GSD "docs-ingest handoff", Kiro "bring architecture docs") rather than re-elicited; a decisions log in a brownfield project should be seeded from existing ADRs, not started empty.
- BMAD's 2026 turn away from storing derived documentation (read source live, keep one verified block) is the strongest counter-signal to "generate many Markdown files about the codebase": derived docs rot; only non-derivable facts should be stored.
- A framework whose first mandatory step is a demand-validation pitch for the whole project has no 2026 peer; all peers accept "a small change to an existing system" as the common case and reserve pitch/review ceremony for genuinely new scope.

### Gaps
- Spec Kit's official existing-project guide content was not retrievable (404); the brownfield details above are from community extensions and an issue.
- Conductor's brownfield initialization mechanism is not documented on the README.

## Key Question 6: Documented failure modes and criticisms of heavyweight methodology plugins, and what lighter 2026 alternatives do instead

### Takeaway
Criticisms cluster around four points: ceremony overhead ("sea of markdown", doubled documentation cost, specs that drift from code), token cost of always-loaded or fully-loaded skills (Superpowers issue #832: 3,150 lines for 14 skills; Conductor and GSD both warn about token use), skill-activation misfires (baseline auto-activation ~50% in one measured study), and over-prompting that models no longer need. Responses in 2026: ceremony that sizes itself (BMAD 6.12, Kiro Quick Spec, Spec Kit bug flow), fewer and shorter skills (BMAD 14→8 core skills, Superpowers reviewer merge), evidence via published evals, derived docs read live instead of stored, and hooks for the few rules that must always hold.

### Cited Findings
- SDD critique **(pre-mid-2026, possibly dated)**: "Keeping specs in sync with changing requirements is costly... the code, spec, and team's mental model drift apart"; SDD "often doubles" overhead; specs capture what, not why; "false confidence"; focus on "field definitions, schemas, and signatures, rather than intent and constraints"; recommends intent-first context with specs only "for stable contracts at system boundaries" (author is a vendor founder) — [dev.to chrisywz, Dec 2, 2025](https://dev.to/chrisywz/the-limits-of-spec-driven-development-3b16)
- Academic framing **(pre-mid-2026, possibly dated)**: three rigor levels "spec-first, spec-anchored, and spec-as-source" with a "decision framework for judging when SDD provides value and when simpler approaches suffice" (submitted Jan 30, 2026, AIWare 2026) — [arXiv 2602.00180](https://arxiv.org/abs/2602.00180)
- Spec Kit usability complaints surfaced in reviews: "a sea of markdown documents, long agent run-times and unexpected friction", engineers "eventually skimming code rather than docs" (secondary summary across reviews; see Gaps) — [dev.to mudassirworks](https://dev.to/mudassirworks/spec-driven-development-what-it-fixes-and-breaks-1co3); [hackernoon first impressions](https://hackernoon.com/spec-driven-development-my-first-impressions-and-opinions)
- OpenSpec's own positioning of Spec Kit: "Thorough but heavyweight", "rigid phase gates and Python setup" — [Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec)
- Superpowers token critique **(pre-mid-2026, possibly dated)**: issue #832 (Mar 19, 2026) cut 14 skills from 3,150 to 977 lines (69%) targeting "rationalization tables, red flags lists, verbose examples, and marketing-style sections", proposing a "lean mode" for Pro users with small quotas; maintainer closed it the same day: "the rationalization tables are there for a reason and are based on extensive testing and real world use" — [obra/superpowers issue #832](https://github.com/obra/superpowers/issues/832); v5.0.4 notes (Mar 16, 2026) admit the plugin "had been over-engineered in places" — [blog.fsck.com v5.0.4](https://blog.fsck.com/releases/2026/03/16/superpowers-v5-0-4); a Chinese post cites issue #190 claiming 22,000+ startup tokens with the plugin installed (unverified) — [juejin](https://juejin.cn/post/7662691781214437412)
- Superpowers' own measurements show which ceremony pays: terse reviewer contract cut reviewer output 41%, narration changes cut another 54%; "plan implementation bodies were marginal"; "up-front planning, strict TDD, and per-change review make builds slower and more expensive, but ... these are the reasons the outcomes are good" — [blog.fsck.com Superpowers 6](https://blog.fsck.com/2026/06/15/Superpowers-6/)
- Google Conductor README: context reading "can increase token use, especially in larger projects or during extended planning and implementation"; **(pre-mid-2026)** README advised disabling Gemini's built-in Plan Mode due to state-management conflict — [conductor](https://github.com/gemini-cli-extensions/conductor); [InfoQ](https://infoq.com/news/2026/01/google-conductor/)
- Skill-activation misfire data **(pre-mid-2026, possibly dated)**: baseline auto-activation 50–55%; indirect phrasing "dropped to near zero"; an llm-eval pre-classifier produced false positives on 4 of 5 unrelated prompts — [scottspence.com](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals)
- Official anti-over-prompting guidance: "Default assumption: Claude is already very smart. Only add context Claude doesn't already have"; "Avoid offering too many options"; "If you keep adding emphasis to a CLAUDE.md line and Claude still misses it, that's a sign the line belongs in a hook"; "if you have hooks for things that are only preferences, delete them and let Claude decide"; "keep the enforced set small" — [skill best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); [code.claude.com best-practices](https://code.claude.com/docs/en/best-practices)
- Official guidance on when to skip planning (per search summary of the best-practices page): plan mode adds overhead for small clear changes; "If you could describe the diff in one sentence, skip the plan" — [code.claude.com best-practices](https://code.claude.com/docs/en/best-practices)
- Ralph-loop critique **(pre-mid-2026)**: "the loop is easy. The check is hard"; each iteration depends on "retaining a clear, unchanged understanding of the original goal"; agent scaffolds "are increasingly good at just continuing until the prompted task is done" — [Tessl](https://tessl.io/blog/unpacking-the-unpossible-logic-of-ralph-wiggumstyle-ai-coding); [ghuntley.com](https://ghuntley.com/ralph/)
- Lighter-weight responses in 2026: BMAD core 14→8 skills and "Build sizes its ceremony after investigating a change" (Sep 2026) — [BMAD releases](https://github.com/bmad-code-org/BMAD-METHOD/releases); Kiro "Quick Spec ... without approval gates" — [kiro.dev/docs/specs](https://kiro.dev/docs/specs/); Spec Kit bug-fix flow as opt-in extension and `/speckit-converge` — [spec-kit](https://github.com/github/spec-kit); GSD "handle-quick-and-fast-tasks", "batch-quick-tasks", "run-phases-autonomously" how-tos — [gsd-core docs](https://github.com/open-gsd/gsd-core/tree/next/docs); OpenSpec `/opsx:ff` fast-forward and free iteration — [OpenSpec](https://github.com/Fission-AI/OpenSpec); Compound Engineering `/lfg` hands-off loop — [compound-engineering-plugin](https://github.com/EveryInc/compound-engineering-plugin); Taskmaster `loop` in a Docker sandbox, one task per iteration — [0.41.0](https://newreleases.io/project/github/eyaltoledano/claude-task-master/release/task-master-ai@0.41.0)
- Third-party benchmark **(unverified methodology)**: a Reenbit comparison reported a CRM dashboard taking 5.5 hours with BMAD versus 12 minutes with OpenSpec — cited via [augmentcode comparison](https://www.augmentcode.com/tools/best-spec-driven-development-tools)
- Third-party "skip the plugin" guidance **(pre-mid-2026)**: pay-for-a-harness criticism "on models that already plan well"; an informal 12-session experiment found ~14% fewer tokens overall but ~8% more on simple tasks with Superpowers — [mcp.directory](https://mcp.directory/blog/superpowers-skill-worth-it-2026); [lzwjava skip-superpowers](https://lzwjava.github.io/skip-superpowers-plugin-en)

### Inferences
- The accepted 2026 defense of ceremony is measurement, not conviction: maintainers who publish with/without evals (Superpowers 6) keep the ceremony that moves the needle (tests, interfaces, review) and cut what does not (plan bodies, narration). A framework that cannot show its delta is presumed to be overhead.
- "Sizes itself to the work" is the dominant design response: a mandatory pitch → CEO review → eng review → milestone → slice → task chain for every change is exactly the "rigid phase gates" OpenSpec and reviewers criticize in Spec Kit; peers now route small changes directly to build-and-verify.
- Token discipline has concrete levers now: fewer, shorter skills; `effort`/`model` per skill (GSD uses `effort: max` only for plan/execute); name-only listing for rare skills; derived docs read live (BMAD); reviewer packets instead of agents re-running git (Superpowers).
- Skill auto-activation is unreliable (~50% measured); frameworks that depend on Claude "choosing" a methodology skill need either an explicit forced-eval hook, user-invoked entry points, or `tool_used: Skill` evals to tune descriptions.

### Gaps
- The "sea of markdown / long run-times" quote reached me via a search aggregate; I could not pin it to a single primary URL with certainty (two candidate posts listed). Treat as representative sentiment, not a verbatim citation.
- The Reenbit 5.5h vs 12min benchmark and the 22k-token Superpowers startup figure are unverified.
- No formal study measuring methodology-plugin ROI (quality vs tokens) beyond Superpowers' self-reported evals was found.

## Key Question 7: Synthesis for the lens: what a plugin shaped like ytstack (artifact-first project OS, pitch/review gates, M###-S##-T## hierarchy, SessionStart injection, PreCompact/SessionEnd handoff+journal, Agent-Teams execution, wrapping superpowers + gstack) is missing or doing in an outdated way, judged against the above

### Takeaway
Measured against H2-2026 practice, the biggest deltas are: no brownfield entry (map-codebase first, pitch only for new scope), no ceremony scaling (quick path for one-sentence diffs), verification living in skill prose instead of Stop/TaskCompleted hooks and pass/fail files, Agent Teams as the primary parallel executor (experimental, non-resumable, token-heavy; peers use orchestrator + worktree subagents), SessionStart injection at risk of the 10,000-char cap and duplicate AGENTS.md loading, hook-written journals that dirty the tree without a commit path or a PR-filter, no shipped evals (`claude plugin eval`, `tool_used: Skill`), skill descriptions competing for a 1%-of-context listing budget, and Claude-Code-only reach while every peer went multi-harness.

### Cited Findings
- All findings above apply; the load-bearing ones are: SessionStart 10,000-char cap and "phrase as factual statements" — [hooks](https://code.claude.com/docs/en/hooks); "A SessionStart hook that prints AGENTS.md: remove it" — [memory](https://code.claude.com/docs/en/memory); Agent Teams "experimental", "No session resumption", "No nested teams", "check whether a lighter option does the job" — [agent-teams](https://code.claude.com/docs/en/agent-teams); Stop hook exit 2 and `TaskCompleted` gates — [best-practices](https://code.claude.com/docs/en/best-practices), [agent-teams](https://code.claude.com/docs/en/agent-teams); `claude plugin eval` v2.1.269+, 3 runs, with/without arms, `--threshold` — [plugin-evals](https://code.claude.com/docs/en/plugin-evals); 1,536-char description cap and 1% listing budget — [skills](https://code.claude.com/docs/en/skills); GSD brownfield flow and `/gsd-pr-branch` — [gsd-core](https://github.com/open-gsd/gsd-core); BMAD "process sizes itself", 14→8 skills, single verified AGENTS.md block — [BMAD](https://github.com/bmad-code-org/BMAD-METHOD), [releases](https://github.com/bmad-code-org/BMAD-METHOD/releases); Kiro Quick Spec and task waves — [kiro specs](https://kiro.dev/docs/specs/); Anthropic feature-list JSON `passes` flag and e2e-before-done — [effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); GSD `HANDOFF.json` consume-once and `DECISIONS-INDEX.md` rollup — [planning-artifacts](https://raw.githubusercontent.com/open-gsd/gsd-core/next/docs/reference/planning-artifacts.md); worktree hook-path caveat — [worktrees](https://code.claude.com/docs/en/worktrees); Superpowers 6 evidence that plan bodies are marginal and reviewers can be merged — [Superpowers 6](https://blog.fsck.com/2026/06/15/Superpowers-6/); subagent `memory: project` committable store — [sub-agents](https://code.claude.com/docs/en/sub-agents).

### Inferences
1. **Brownfield entry is missing.** Peers start existing projects with a codebase map (GSD: 7 files from 4 parallel mappers; Kiro: product/tech/structure; BMAD: one verified block) and ingest existing ADRs/README; the pitch (office-hours) is reserved for new scope. A framework whose scaffold step requires a validated pitch has no brownfield door.
2. **Ceremony does not scale down.** Fixed gates (pitch → CEO → eng → milestone → slice → task) for every change contradict BMAD 6.12 ("Build sizes its ceremony"), Kiro Quick Spec, Spec Kit's bug-fix flow, and Anthropic's "if you could describe the diff in one sentence, skip the plan". A quick lane (one task, one summary, verification only) is the 2026 baseline.
3. **Verification should be harness-enforced.** "Verification before completion" as a skill is the weak form; peers use a Stop hook (exit 2 until the check passes), `TaskCompleted` hooks for teams, a machine-readable status (`VERIFICATION.md status:` enum, `passes` JSON), and a fresh read-only reviewer subagent. Summaries should not be writable while the verification file says failed.
4. **Agent Teams as the primary executor is outdated.** Teams are experimental, cannot resume, cannot nest, auto-approve teammate plans unless modes are changed, and cost significantly more; peers (GSD, Compound Engineering, Superpowers, Kiro waves) use an orchestrator that never edits source plus fresh subagents with `isolation: worktree` and file-ownership partitioning. Teams remain appropriate for debate-style review and competing hypotheses.
5. **SessionStart injection needs a budget and de-duplication.** Keep the injected briefing under 10,000 characters, phrase it as facts, and do not print AGENTS.md/CLAUDE.md content that Claude already loads (now native since v2.1.277). Use the `compact`/`resume` matchers to refresh only the delta.
6. **Handoff/journal writes need a storage decision.** Either commit them through a CLI with a `docs(...)` message and provide a PR-filter (GSD `/gsd-pr-branch` strict), or write them to a user-dir/consume-once location (`HANDOFF.json` style, Claude's own `~/.claude/projects/.../memory/`). Hook-written files that are neither committed nor ignored produce the FastSense #168 failure. Hooks must also use the input `cwd`, not `${CLAUDE_PROJECT_DIR}`, when a session is in a worktree.
7. **Append-only DECISIONS.md needs a rollup.** GSD generates `DECISIONS-INDEX.md` once prior CONTEXT files exceed a read threshold; Claude's auto memory loads only the first 200 lines / 25KB of an index. An ever-growing append-only log with no index will stop being read in full.
8. **KNOWLEDGE.md overlaps with built-in memory.** Auto memory (per repo, shared across worktrees) and subagent `memory: project` (`.claude/agent-memory/<name>/`, committable) now exist; a framework knowledge file should either be the committed, team-visible layer that those feed, or be shaped like them (one-line index + topic files). BMAD's rule "anything derivable from source is read live rather than stored" argues against storing codebase facts at all.
9. **No evals, no claim.** Peers ship `evals/` and publish with/without deltas; `claude plugin eval` makes this a CI step. Skill-activation evals (`tool_used: Skill`) are the first thing to run because baseline auto-activation measured ~50%.
10. **Skill-description budget.** With 20+ skills and long descriptions, the 1,536-char cap and 1% listing budget will drop descriptions of least-used skills, breaking auto-activation. Front-load trigger terms, shorten, and mark rarely used skills `name-only` or `disable-model-invocation`.
11. **Single-harness.** Every peer is multi-harness (GSD, BMAD, Superpowers 6, Compound Engineering, OpenSpec, Spec Kit, Taskmaster). This is a strategic gap rather than a mechanism gap; Compound Engineering's converter CLI and BMAD's `npx skills add` show the common approach (skills as the portable unit).
12. **Living spec layer.** Peers keep a "current truth" spec (OpenSpec `openspec/specs/`, Spec Kit converge/Living Specs, Kiro requirements with EARS) separate from per-change plans; a plan/summary-only hierarchy has no place where the system's current behaviour is specified after many tasks.
13. **Effort/model per skill.** GSD declares `effort: max` for plan/execute and `effort: low` for status skills; Claude Code supports `effort`, `model`, `context: fork` in skill frontmatter. Uniform effort across all skills leaves cost on the table; note GSD's lesson that `context: fork` breaks skills that must spawn subagents.
14. **Wrapping vendored skills.** Superpowers 6 itself merged reviewers and found plan bodies marginal; a wrapper that preserves every vendored step inherits ceremony the upstream has since trimmed. Re-check which vendored steps the upstream's own evals keep.

### Gaps
- These inferences are judged against public docs and peer frameworks, not against measurements of the framework in question; the only way to confirm the token/ceremony claims for a specific plugin is to run `claude plugin eval` with and without it.
- Whether the Agent Teams limitations (resume, nesting) will be lifted soon is unknown; the docs still mark the feature experimental as of 2026-11-07.
