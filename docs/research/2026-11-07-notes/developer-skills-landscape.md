# Developer-skills landscape for AI coding agents (state: 2026-11-07)

Research note for the ytstack modernisation. Companion to the sibling notes in this folder (`claude-code-platform-changes.md` covers the Claude Code skill/plugin surface in depth; this note covers the *content* side: which skill collections developers actually use, what the best ones look like, and what that implies for ytstack).

Method: every star count, date, file size and tree listing below comes from the GitHub REST API via `gh api` on 2026-11-07 (not from memory); skill bodies were fetched raw from the repos; docs were fetched from code.claude.com, platform.claude.com, agentskills.io, skills.sh. Anything whose source predates mid-2026 is marked "(possibly dated)". Facts and judgement are kept in separate sections: "Cited Findings" is fact, "Inferences" and the final "Recommendations for ytstack" are my judgement and reference the facts.

Four key questions:

1. `mattpocock/skills` in detail
2. Top developer-skill collections overall, and the 10-15 individual skills that recur
3. Quality criteria and anti-patterns (official docs + leading authors)
4. "ponytail"

## Key question 1: `mattpocock/skills`

### Takeaway

`mattpocock/skills` ("Skills for Real Engineers") is, by GitHub stars, the single most-starred skill collection on GitHub as of 2026-11-07 (317,160 stars, created 2026-02-03), and by skills.sh installs the most-installed developer-process skill set (`grill-me` 1.5M installs, #2 all-time behind `find-skills`). It ships **27 promoted skills** (20 engineering, 7 productivity) as a Claude Code plugin in the official marketplace (`mattpocock-skills@claude-plugins-official`, v1.3.2 released 2026-10-29), plus Codex/Copilot marketplaces and `npx skills add` for everything else. Its design is the opposite of ytstack's: skills are **tiny** (median ~70 lines, three are one sentence), there is **no shared preamble, no required sections, no sentinel files, no AskUserQuestion**; every skill is either **user-invoked** (`disable-model-invocation: true`, human-facing description) or **model-invoked** (rich trigger description), and skills call each other only via the literal instruction "Call the Skill tool with X". The philosophy is written down in the model-invoked `writing-for-agents` skill (context pointers, two loads, information hierarchy, leading words, no-op pruning) and in a strict `SCOPE.md` + `.out-of-scope/` rejection ledger.

**Shipped skills** (`.claude-plugin/plugin.json` `skills` array, 27 entries; one-liners from README):

Engineering, user-invoked (`disable-model-invocation: true`):
- `ask-matt` -- router: "Ask which skill or flow fits your situation."
- `grill-with-docs` -- grilling session that also builds the domain model (`GLOSSARY.md` + ADRs). Body is one line: `Call the Skill tool twice, for "grilling" and "domain-modeling".`
- `triage` -- move issues/external PRs through a state machine of triage roles, write agent-ready briefs.
- `improve-codebase-architecture` -- scan for deepening opportunities, HTML report, then grill through one.
- `setup-matt-pocock-skills` -- per-repo config (tracker, labels, doc layout).
- `to-spec` -- turn the current conversation into a spec on the tracker; "no interview, just synthesis".
- `to-tickets` -- break plan/spec into tracer-bullet tickets with blocking edges.
- `implement` -- 17 lines: fetch ticket, "Call the Skill tool with tdd where possible, at pre-agreed seams", typecheck regularly, "call the Skill tool with code-review", commit.
- `implement-spec` -- whole spec on one integration branch, implementer subagents across the ready frontier, closes with `code-review`.
- `wayfinder` -- plan work larger than one session as decision tickets on the tracker.
- `retro` -- suggest improvements to the agent's *environment* (navigation pointers, automated checks, coding standards, steering files, tool economy, information access), most severe first; mechanical violations get a deterministic check, `CODING_STANDARDS.md` is for judgement calls only.

Engineering, model-invoked:
- `prototype` -- throwaway prototype (single HTML file for logic, or several UI variations on one route).
- `diagnosing-bugs` -- 138 lines, six phases: build a feedback loop ("This is the skill. Everything else is mechanical."), reproduce + minimise, 3-5 falsifiable hypotheses, instrument with `[DEBUG-xxxx]` tags, regression test before fix, cleanup checklist.
- `research` -- 12 lines: background agent, fresh context, primary sources, cited Markdown file in the repo.
- `tdd` -- 38 lines + `tests.md` + `mocking.md`: seams agreed up front, three anti-patterns (implementation-coupled, tautological, horizontal slicing), "Refactoring is not part of the loop."
- `domain-modeling` -- build/sharpen `GLOSSARY.md` and ADRs inline.
- `codebase-design` -- shared vocabulary for deep modules (module, interface, depth, seam, adapter, leverage, locality); referenced by `tdd`.
- `code-review` -- two axes (Standards incl. a fixed Fowler smell baseline; Spec vs originating issue) as two parallel fresh-context subagents, reports kept separate, "Under 400 words" each.
- `pr` -- PR body template: Summary as "the smallest visual that makes the change clear", Evidence (before/after), Merge Danger (one-way/two-way door, blast radius). Credits Dex Horthy's `show-me` (humanlayer/skills) in `metadata.credits`.
- `wizard` -- generate an interactive bash wizard for steps only a human can do.

Productivity, user-invoked: `grill-me` (one line: `Call the Skill tool with "grilling".`), `handoff` (to `$TMPDIR`, redact secrets, "suggested skills" section), `teach`, `to-questionnaire`, `wait-what`.
Productivity, model-invoked: `grilling` (the interview primitive: design tree, frontier, rounds, recommended answer per question, "Word each question so yes accepts your recommended answer", facts fetched by subagent, decisions by the user), `writing-for-agents`.

Not shipped (public, `in-progress/`): `chief-of-staff`, `claude-handoff`, `loop-me`, `setup-ts-deep-modules`, `software-factory`, `writing-beats/fragments/shape`. **Structure and length** (measured `wc -l` on the 27 shipped `SKILL.md` files, 2026-11-07): 7, 7, 7, 12, 16, 17, 26, 30, 38, 42, 44, 44, 54, 71, 74, 75, 81, 89, 97, 105, 112, 114, 120, 128, 138, 140, 170 lines; total 1,957 lines across 27 skills (mean 72). Frontmatter uses only `name`, `description`, optional `disable-model-invocation`, `argument-hint`, `metadata`. No `tier`, `version`, `allowed-tools`, no required sections, no XML gates, no checklists. Supporting files are flat siblings (`tests.md`, `mocking.md`, `DEEPENING.md`, `PHASE-BOUNDARIES.md`, `ADR-FORMAT.md`), not a `references/` dir. Cross-skill dependencies are expressed as `Call the Skill tool with "<name>"` (never `/name` prose, never `../other-skill/FILE.md`). -- `.agents/invocation.md`: "Naming the tool is what gets it fired ... spelling that out gets a higher hit rate than dropping a /name into prose." https://github.com/mattpocock/skills/blob/main/.agents/invocation.md

**Stated philosophy** (README "Why These Skills Exist"): four failure modes and fixes: (1) "The Agent Didn't Do What I Want" -> grilling; (2) "The Agent Is Way Too Verbose" -> shared language (`GLOSSARY.md`); (3) "The Code Doesn't Work" -> feedback loops, `/tdd`, `/diagnosing-bugs`; (4) "We Built A Ball Of Mud" -> `/to-spec` module quiz, `/improve-codebase-architecture`. Positioning: "Approaches like GSD, BMAD, and Spec-Kit try to help by owning the process. But while doing so, they take away your control and make bugs in the process hard to resolve. These skills are designed to be small, easy to adapt, and composable. They work with any model." -- https://github.com/mattpocock/skills/blob/main/README.md. aihero.dev "5 agent skills I use every day" (updatedAt 2026-03-16, possibly dated): "Skills don't have to be long to be impactful. You just need to choose the right words at the right time." -- https://www.aihero.dev/5-agent-skills-i-use-every-day

**`writing-for-agents` doctrine** (81 lines, model-invoked; https://github.com/mattpocock/skills/blob/main/skills/productivity/writing-for-agents/SKILL.md and `SKILL-MECHANICS.md`):
- Context pointer: "The pointer's wording, not its target, decides when the agent reaches the material ... A must-have target behind a weakly worded pointer is a variance bug: sharpen the wording first, and inline the material only if sharpening fails." Pointer rules: front-load the leading word, one trigger per branch, cut identity the body already carries.
- Two loads: context load (always-loaded text) vs cognitive load (the human as index). "Pick model-invocation only when the agent must reach the skill on its own, or another skill must. If it only ever fires by hand, make it user-invoked and pay no context load."
- Information hierarchy: in-file step > in-file reference > disclosed reference. "Progressive disclosure is the move down the ladder ... Not primarily a token optimisation: it is how the hierarchy is protected."
- Completion criteria: every step ends on a checkable, exhaustive criterion ("Every modified model accounted for" vs "produce a change list").
- Leading words: reuse pretrained concepts (_tight_, _red_, _tracer bullets_) instead of restating; "Negation is the failure mode beside this lever: steering by prohibition drags the forbidden behaviour into context ... Prompt the positive."
- Pruning: single source of truth; the environment is a source of truth ("a document that restates it is a cache"); relevance; "Hunt no-ops sentence by sentence: an instruction the model already obeys by default pays load to say nothing ... delete the whole sentence rather than trim words from it."
- Router skills: when user-invoked skills multiply, one user-invoked router (`ask-matt`) names them; it "can only hint, never fire them".

**Scope discipline** (`SCOPE.md`, `.out-of-scope/`): issues must describe an "Observed failure" and "Fit the philosophy"; new-skill proposals are closed ("if you can compose the behaviour from existing skills, it doesn't get a new skill"); grilling via `AskUserQuestion` is explicitly rejected ("Structured pickers push the model towards multiple-choice questions with pre-baked answers, which is the opposite of what grilling is for ... I've tried the AskUserQuestion UI and don't want it in these skills"); no question caps; no anti-recursion guards in skills ("The harness should be responsible for stopping infinite subagent loops, not skills"). -- https://github.com/mattpocock/skills/blob/main/SCOPE.md, https://github.com/mattpocock/skills/blob/main/.out-of-scope/native-question-tool.md, .../new-skills.md, .../question-limits.md, .../subagent-recursion.md

**Repo-wide rules** (`AGENTS.md`): promoted skills must appear in README + plugin.json; every skill has a docs page with four sections (What it does / When to reach for it / Common questions / It's working if); `ask-matt` must be re-synced on every skill change ("a router that lies"); no em-dashes anywhere; "Every skill that dispatches a subagent says to start it with a fresh context window" (because Codex forks by default). -- https://github.com/mattpocock/skills/blob/main/AGENTS.md

### Inferences

- The repo's size discipline is real, not marketing: 27 skills in 1,957 lines total is smaller than ytstack's single `init-project` (385 lines) plus `summarize-task` (306) plus `plan-milestone` (303).
- The user-invoked/model-invoked split is doing the work ytstack's `tier:` field was meant to do (which skills cost context all the time), but with a mechanism Claude Code actually enforces (`disable-model-invocation`) instead of a label.
- The skills most valuable for a software-development OS, by overlap with ytstack's spine: `grilling` (replaces/complements office-hours forcing questions with an open, round-based interview), `tdd` (seams-first, shorter than superpowers'), `diagnosing-bugs` (feedback-loop-first; sharper than superpowers `systematic-debugging` on *how* to get a repro), `code-review` (two-axis, parallel fresh-context subagents, Spec axis maps directly onto a ytstack task-plan), `pr` (PR body with evidence + merge danger; ytstack has nothing for PRs), `retro` (environment retro feeding KNOWLEDGE.md/hooks/checks), `research` (background cited notes, exactly how this note was produced), `writing-for-agents` (a skill-authoring reference that ytstack's `docs/ux/*.md` could be measured against), `handoff` (overlaps `handoff-session`; the `$TMPDIR` + "suggested skills" + redaction details are better).
- Weak fit: `triage`, `wayfinder`, `to-tickets`, `implement-spec` assume an issue tracker as the artifact store; ytstack's artifact store is `.ytstack/`. `setup-matt-pocock-skills` is a per-repo onboarding pattern ytstack already has in `init-project`.

## Key question 2: top developer skills overall

### Takeaway

The 2026 landscape has consolidated into (a) five or six **process/method** collections above 100k stars (`mattpocock/skills` 317k, `obra/superpowers` 314k, `affaan-m/ECC` 299k, `anthropics/skills` 188k, `DietrichGebert/ponytail` 186k, `garrytan/gstack` 141k, `addyosmani/agent-skills` 114k), (b) **aggregators/registries** (`skills.sh` + `vercel-labs/skills` CLI 38k, `ComposioHQ/awesome-claude-skills` 79k, `hesreallyhim/awesome-claude-code` 57k, `sickn33/agentic-awesome-skills` 49k, `VoltAgent/awesome-agent-skills` 37k), and (c) the **official Claude Code marketplace** (317 plugins, 46k stars on the directory repo). The dominant install model is now "plugin from a marketplace with auto-update" for Claude Code/Codex/Copilot, and `npx skills add <owner/repo>` for everything else. The individual skills that recur across every serious collection are: brainstorming/grilling, writing plans, TDD, systematic debugging, verification before done, code review (multi-axis or multi-agent), PR/commit, handoff, worktree isolation, writing skills, retro/compound (learning capture), frontend-design/anti-slop, and lately a YAGNI/minimal-code guard (ponytail).

## Key question 3: quality criteria and anti-patterns

### Takeaway

Four sources now agree on the core rules and disagree on two points. Agreement: `description` is the trigger (third person, what + when, key terms, key use case first); body under 500 lines (Claude Code docs, agentskills.io, platform best practices, skill-creator all say so); progressive disclosure via sibling files referenced one level deep; concise ("Claude is already very smart"); feedback loops / validators; build evals before writing more prose; test triggering with should/should-not prompts. Disagreement 1: Anthropic's skill-creator says "make the skill descriptions a little bit pushy" and "explain the why" and treats ALWAYS/NEVER in caps as a warning sign; superpowers says the opposite on style (hard gates, Red Flags tables, "pressure testing") and explicitly refuses "compliance" rewrites, while agreeing that descriptions must *not* summarise the workflow ("Claude may follow the description instead of reading the full skill"). Disagreement 2: superpowers wants descriptions to start "Use when..." and describe *only* triggering conditions; Anthropic wants "what it does AND when". Mattpocock sits closer to Anthropic on tone (positive phrasing, no-op pruning, no negation) and closer to superpowers on terseness. The Claude Code platform adds hard numbers the authors did not have earlier: 1,536-char cap per listing entry, 1% context budget for the whole listing, `/skill-doctor`, `claude plugin eval`.

### Cited Findings

**Claude Code docs, Skills page** (https://code.claude.com/docs/en/skills, fetched 2026-11-07):
- "Put the key use case first: the combined `description` and `when_to_use` text is truncated at 1,536 characters in the skill listing to reduce context usage."
- "Keep `SKILL.md` under 500 lines. Move detailed reference material to separate files."
- "Keep the body itself concise. Once a skill loads, its content stays in context across turns, so every line is a recurring token cost. State what to do rather than narrating how or why."
- `disable-model-invocation: true`: "Claude can't invoke the skill on its own. Use this for workflows with side effects or that you want to control timing." `user-invocable: false`: "Only Claude can invoke the skill. Use this for background knowledge that isn't actionable as a command."
- `context: fork` "doesn't run in a fork of the current conversation" and "only makes sense for skills with explicit instructions"; `background` default `true` (opt out with `background: false`).
- `hooks`: "Hooks that Claude Code registers when the skill is invoked and keeps running for the rest of the session." `paths`: globs that limit activation.
- "A field name must match the table exactly, hyphens included: Claude Code ignores a field it doesn't recognize without reporting an error."
- `/skill-doctor`: "see what each of your skills costs and how often it gets used, so you can decide which ones to turn off."
- Plugin evals: "`claude plugin eval` runs each prompt in an isolated session with and without the plugin, scores it with graders you define or that it writes for you, and exits non-zero below a threshold so you can gate CI on it."
- Security: "Workspace trust doesn't gate this field. Claude Code applies a project skill's `allowed-tools` even in a `-p` run in a folder you've never trusted."
- The 1% listing budget, `skillListingBudgetFraction`, `skillOverrides: name-only`, 5,000/25,000-token re-attach after compaction and the `/doctor prompt-audit` command are documented in detail in the sibling note `claude-code-platform-changes.md` (lines 107-122) with the same source URL.

**Anthropic "Skill authoring best practices"** (https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices, fetched 2026-11-07):
- "Concise is key ... The context window is a public good." "Default assumption: Claude is already very smart. Only add context Claude doesn't already have."
- Degrees of freedom: high (text heuristics) for code review, low (exact script) for migrations; "Narrow bridge with cliffs on both sides ... Open field with no hazards".
- Frontmatter limits: `name` max 64 chars, lowercase/numbers/hyphens, no reserved words `anthropic`/`claude`; `description` max 1,024 chars, non-empty, no XML tags. Prefer gerund names (`processing-pdfs`).
- "Always write in third person. The description is injected into the system prompt."
- "Keep the SKILL.md body under 500 lines"; "Keep references one level deep from SKILL.md"; "For reference files longer than 100 lines, include a table of contents."
- Workflows: "provide a checklist that Claude can copy into its response and check off"; feedback loop "Run validator -> fix errors -> repeat".
- "Avoid time-sensitive information"; "Use consistent terminology"; "Avoid offering too many options" (give a default with an escape hatch); "Avoid Windows-style paths".
- "Create evaluations BEFORE writing extensive documentation"; "At least three evaluations created"; "Tested with Haiku, Sonnet, and Opus". Note the evaluation JSON example is marked "There is not currently a built-in way to run these evaluations" (possibly dated relative to `claude plugin eval`).
- "You don't need special system prompts or a 'writing skills' skill to get Claude to help create Skills."

**Agent Skills specification** (https://agentskills.io/specification, fetched 2026-11-07): required `name` (1-64, lowercase, hyphens, must match directory) and `description` (1-1024 chars); optional `license`, `compatibility` (max 500), `metadata` (string map), `allowed-tools` (experimental, space-separated). Layout `SKILL.md` + optional `scripts/`, `references/`, `assets/`. Progressive disclosure: "Metadata (~100 tokens) ... Instructions (< 5000 tokens recommended) ... Resources (as needed)"; "Keep your main SKILL.md under 500 lines"; "Keep file references one level deep". Validator: `skills-ref validate ./my-skill`.

**anthropics/skills `skill-creator`** (https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md, 33 KB): "include both what the skill does AND specific contexts for when to use it"; "make the skill descriptions a little bit 'pushy'" because Claude undertriggers; "Keep SKILL.md under 500 lines"; "For large reference files (>300 lines), include a table of contents"; "explain the why", heavy ALWAYS/NEVER in caps is a warning sign; evals: 2-3 realistic prompts in `evals/evals.json` first, with-skill vs baseline runs in the same turn, `benchmark.json`/`benchmark.md` (pass rate, time, tokens), optional blind A/B; description tuning: 20 queries (8-10 should-trigger, 8-10 near-miss should-not-trigger), 60/40 train/held-out split, 3 runs each, up to 5 iterations, pick by held-out score. Official marketplace entry: `skill-creator` "Create new skills, improve existing skills, and measure skill performance".

**superpowers `writing-skills`** (vendored copy `vendor/superpowers/skills/writing-skills/SKILL.md`; upstream https://github.com/obra/superpowers/blob/main/skills/writing-skills/SKILL.md): "Writing skills IS Test-Driven Development applied to process documentation" (baseline scenario without skill -> document rationalizations -> write skill -> re-verify). Description: "Third-person, describes ONLY when to use (NOT what it does) ... Start with 'Use when...' ... NEVER summarize the skill's process or workflow ... Keep under 500 characters if possible." CSO rationale: "A description saying 'code review between tasks' caused Claude to do ONE review, even though the skill's flowchart clearly showed TWO reviews." Word budgets: getting-started <150 words, frequently-loaded <200, others <500. "Don't create for ... Mechanical constraints (if it's enforceable with regex/validation, automate it ... save documentation for judgment calls)." Cross-reference with `**REQUIRED SUB-SKILL:**`, never `@` links ("force-loads files immediately"). Upstream `CLAUDE.md`: "Skills are not prose -- they are code that shapes agent behavior ... Run adversarial pressure testing across multiple sessions; Show before/after eval results in your PR" and the refusal of "compliance" rewrites quoted in Q2.

**mattpocock `writing-for-agents`**: see Q1 (context pointers, two loads, information hierarchy, completion criteria, leading words, negation, no-op pruning, single source of truth, environment as source of truth). Also `AGENTS.md`: no em-dashes; subagents always start with a fresh context window; dependencies as "Call the Skill tool with".

**gstack `write-skill`**: "edit ladder (fix the tool first, add nothing the model already does, edit the line instead of appending, lowest level that reaches the agent, rule not story)", `gstack-skill-bill` size-per-level and "growth since the last diet", "full diets proven by a before/after/no-skill test" -- https://github.com/garrytan/gstack/blob/main/write-skill/SKILL.md

**Independent critique of untested skills** (Colin Eberhardt, Scott Logic, 2026-06-16, on ponytail): "I'm yet to see a Skills library on GitHub that has a comprehensive test or evaluation suite (or any test suite for that matter)"; a seven-word prompt ("Follow YAGNI principles, and one-liner solutions") beat ponytail's own LOC benchmark (6.9 vs 8.25 LOC at 100% correctness); "If they don't have a decent benchmark that substantiates their claims" they are "riding the hype wave". -- https://blog.scottlogic.com/2026/06/16/ponytail-yagni-and-the-problem-with-prompt-benchmarks.html; InfoQ follow-up 2026-08: https://infoq.com/news/2026/08/ponytail-agent-skill-benchmark

**Consolidated do / don't list** (each item carries its source above):

Do:
- Description = third person, what + when, specific key terms, key use case first (Claude Code docs, platform best practices, agentskills.io, skill-creator). Keep it well under the 1,536-char listing cap and the 1,024-char spec max; superpowers/mattpocock aim for one or two sentences.
- Never summarise the procedure in the description (superpowers CSO; mattpocock "cut identity the body already carries").
- Body < 500 lines (all official sources); in practice the respected collections are far below: mattpocock mean 72 lines, superpowers 3-20 KB, ponytail 3.5 KB.
- One level of references, named descriptively, with a TOC above 100 (platform) / 300 (skill-creator) lines.
- Checklists the agent copies; validator loops; exact scripts where the path is fragile (platform best practices).
- Decide invocation explicitly: `disable-model-invocation: true` for side-effect / human-timed workflows; `user-invocable: false` for background knowledge (Claude Code docs; mattpocock makes this the primary axis).
- Dependencies between skills as an explicit tool call ("Call the Skill tool with X" / `REQUIRED SUB-SKILL:`), never `@file` or bare `/name` (mattpocock invocation.md; superpowers).
- Subagents start with a fresh context window, stated in the skill (mattpocock AGENTS.md, changelog #1341).
- Evals first: 2-3 prompts, baseline vs with-skill, should/should-not trigger set, then `claude plugin eval` in CI with a `tool_used: Skill` grader (skill-creator; Claude Code plugin-evals; sibling note lines 172-190).
- Measure the always-on cost with `/skill-doctor` and `claude plugin details <plugin>`; prune or `name-only` low-use skills (Claude Code docs).
- Prune no-ops sentence by sentence; do not restate what `package.json`/`--help`/the repo layout already say (mattpocock; superpowers "Move details to tool help").
- Mechanical rules go into a linter/hook/CI check, not prose (superpowers "Don't create for mechanical constraints"; mattpocock `retro`).

Don't:
- Don't narrate why/how in the body ("State what to do rather than narrating how or why" -- Claude Code docs) and don't add explanation Claude already has (platform).
- Don't steer by prohibition when a positive target exists ("Don't think of an elephant" -- mattpocock); skill-creator flags heavy ALWAYS/NEVER caps. (Superpowers disagrees in practice; its hard gates are deliberate and eval-tuned.)
- Don't use time-sensitive statements, inconsistent terms, multiple equal options, Windows paths, nested reference chains (platform).
- Don't depend on `CLAUDE.md`, `~/.claude`, other plugins or `.ytstack/` existing inside eval runs: "Nothing personal or project-level loads" (plugin-evals, via sibling note line 178).
- Don't let a skill grant itself broad `allowed-tools` casually; it applies even in untrusted `-p` runs (Claude Code docs).
- Don't ship a skill library without a public eval or benchmark (Eberhardt; superpowers CLAUDE.md; gstack diets).
- Don't make a `disable-model-invocation` skill a dependency of another skill: "no other skill can call it" (mattpocock invocation.md).

### Inferences

- The field has converged on *measurement* as the mark of a serious skill: skill-creator evals, `claude plugin eval`, superpowers pressure tests, gstack before/after/no-skill diets, ponytail's 585-session benchmark. A skill set with none of these is now the exception among top collections.
- The one real schism, superpowers' gate-heavy style vs Anthropic/mattpocock's lean positive style, is not resolved by evidence either side publishes in the repo; superpowers claims eval tuning, mattpocock claims a 63% token reduction at v1.0. Picking a side for ytstack should be done by running `claude plugin eval` on both styles of wrapper, not by taste.

### Gaps

- The Claude Code Skills page was read up to 100,000 of 118,986 characters; the 1% budget paragraph is cited via the sibling note, which read the full page.
- No source quantifies the triggering benefit of `when_to_use` vs a longer `description`; skill-creator's tuning loop is the only published method.
- `agnix` (SKILL.md linter, 472 stars) and `skills-ref validate` were not run against ytstack.

## Recommendations for ytstack

Judgement section. Each item points at the facts above; none of it has been tried in ytstack yet.

1. **Cut wrapper descriptions to triggers only and measure them.** ytstack's `test-driven-development` description is "RED-GREEN-REFACTOR: write a failing test, watch it fail, write minimal code, watch it pass, commit. Thin ytstack wrapper around the vendored superpowers ... Use during task execution." That is exactly the pattern superpowers' own `writing-skills` documents as harmful ("Claude may follow the description instead of reading the full skill"), and it spends 1,536-char-capped listing budget on implementation detail (Q3). Rewrite every ytstack description as third-person what + when (Anthropic) or "Use when..." (superpowers), drop "Thin ytstack wrapper around ..." from all of them (that identity belongs in the body), and verify with skill-creator's should/should-not set plus a `claude plugin eval` `tool_used: Skill` grader (sibling note line 175).

2. **Adopt the user-invoked / model-invoked split as the primary axis, replacing or demoting `tier:`.** `tier: core|task|background` is a ytstack label with no runtime effect; `disable-model-invocation: true` and `user-invocable: false` are enforced by Claude Code (Q3) and are the organising principle of the most-installed collection (Q1). Candidates for `disable-model-invocation: true` (human-timed, side effects): `init-project`, `plan-milestone`, `slice-milestone`, `spawn-milestone-team`, `summarize-task`, `handoff-session`, `reassess-roadmap`. Candidates for `user-invocable: false` (pure reference): `atomic-design`, `software-craftsmanship`, `oss-project`, the two `*-api` skills. Then run `/skill-doctor` to see what the listing still costs.

3. **Shrink the procedure skills toward the 100-line class and push the rest down one level.** ytstack's 21 skills total ~3,500 lines of wrapper text *plus* vendored bodies inlined via `!cat` (TDD alone pulls 9.6 KB of superpowers text into context on every invocation). mattpocock ships 27 skills in 1,957 lines; ponytail's core is 3.5 KB; even superpowers' heaviest is 20 KB. Concretely: move the 30-line `## ytstack context` resolver block that is repeated in every wrapper into one shared script the skill *runs* (platform best practices: "Prefer scripts for deterministic operations"; gstack does this with `gstack-skill-start`), keep one `references/` file per skill for the Preamble/Terminal-State boilerplate, and apply mattpocock's no-op test sentence by sentence to the Checklist/Process Flow sections.

4. **Add the five recurring skills ytstack lacks, as thin skills over existing artifacts (Q2 list):**
   - `code-review` two-axis (Standards vs Spec) with the Spec axis reading `M###-S##-T##-PLAN.md`, run as two fresh-context subagents (mattpocock `code-review`; official `code-review` plugin shows the multi-agent form is mainstream).
   - `pr` body = Summary visual + Evidence (before/after) + Merge Danger (door + blast radius); the Evidence section is the natural home for `verification-before-completion` output (mattpocock `pr`, humanlayer `show-me`).
   - `retro` that writes to `KNOWLEDGE.md`/hooks/CI instead of a tracker, with mattpocock's rule "mechanical violation -> deterministic check, prose only for judgement calls" (also superpowers "Don't create for mechanical constraints"); this is the "compound" step every method framework now has (compound-engineering `ce-compound`, gstack `retro`/`learn`).
   - `research` as a background fresh-context agent writing a cited note into `docs/research/` (mattpocock `research`; this note is the format).
   - `grilling`-style open interview as an alternative or front-end to `office-hours`' six forcing questions: round-based, frontier-ordered, recommended answer per question, facts fetched by subagent, "yes accepts the recommendation" (mattpocock `grilling`). Note the explicit tension with ytstack's AskUserQuestion contract: mattpocock rejects the widget for grilling (`.out-of-scope/native-question-tool.md`), gstack embraces it with tuning hooks. Decide per skill, and treat `docs/ux/askuserquestion-format.md` as applying to decision gates, not to open interviews.

5. **Consider wrapping or adopting a minimal-code guard.** ponytail (186k stars) and the official `code-simplifier`, compound `ce-simplify-code`, addyosmani `code-simplification` show demand for an always-on YAGNI guard with a test rule and a `shortcut:` debt ledger (Q4). ytstack's `software-craftsmanship` is a passive reference. Either reference ponytail as an optional sibling plugin (ponystack shows gstack + ponytail compose) or lift the six-rung ladder + "never cut" list into `software-craftsmanship` and make it `user-invocable: false` background knowledge. Do not copy prose verbatim (ytstack CLAUDE.md rule; ponytail is MIT so attribution in `NOTICE` would suffice if lifted).

6. **Ship evals and a public benchmark, or stop claiming quality.** Every serious collection now has one: skill-creator evals, superpowers pressure tests, gstack before/after/no-skill diets, ponytail's 585-session harness and 26 test files; Eberhardt's critique ("I'm yet to see a Skills library ... that has a comprehensive test or evaluation suite") is the reputational risk. ytstack has `tests/*.test.sh` for hooks and `bin/ytstack-check` for structure but nothing that tests whether a skill *fires* or *changes behaviour*. Add `evals/<case>/prompt.md` + graders for the five spine skills and run `claude plugin eval . --trust-plugin --json results.json --threshold 0.8 ... --no-publish --max-cost-usd 20` in CI (recipe in sibling note line 177). Because eval runs load nothing project-level, each case needs a `scaffold_script` that creates the `.ytstack/` fixtures.

7. **Distribution: get on skills.sh and keep the marketplace path auto-updating.** Discoverability in 2026 happens on skills.sh (grill-me 1.5M installs) and in marketplaces with auto-update (Q2). ytstack is only in `yesterday-public-plugins`. A skills.sh listing costs nothing beyond a valid SKILL.md tree (`npx skills add Yesterday-AI/ytstack` would work today if the frontmatter validates; note mattpocock's incident where unquoted colons in `description` made skills.sh skip six skills, changelog 1.3.0 #911). Add `license` and a quoted `description` to every frontmatter and run `skills-ref validate`.

8. **Write down the invocation convention mattpocock uses.** "Call the Skill tool with X" and "start the subagent with a fresh context window" are two one-line rules that removed whole classes of bugs in that repo (changelog #878, #1341). ytstack wrappers reference each other as `ytstack:plan-task` in prose; `.ytstack/DECISIONS.md` should fix one form and `bin/ytstack-check` can lint it.

9. **Harness-portability is a 2026 baseline, not a differentiator.** superpowers (15 harnesses), gstack (`--host` x12), ponytail (20 agents), mattpocock (6 install routes), compound (14 hosts) all ship multi-harness. ytstack's `!` shell blocks and `${CLAUDE_SKILL_DIR}` already have a Codex fallback branch in the resolver; if portability is a goal, ponytail's `docs/agent-portability.md` and `scripts/check-rule-copies.js` (byte-identical rule copies checked in CI) are the cheapest pattern to copy; if not, say so in `docs/concept.md` so nobody spends effort on it.

10. **Keep what the evidence does not argue against.** Nothing in the top collections argues against ytstack's artifact model (`PROJECT.md`, `DECISIONS.md`, `KNOWLEDGE.md`, `STATE.md`); mattpocock's `GLOSSARY.md` + ADRs, compound's `docs/solutions/`, gstack's design docs and `.gstack/` all converge on committed project artifacts that skills read and write. The modernisation is about the *skill layer* (size, triggers, invocation, evals, missing skills), not the artifact layer.
