## What this does

`init-project` writes the technical spec after the six artifacts. It proposes three to eight areas from the pitch and its reviews and confirms the list in one question; in non-interactive mode it takes the proposal and logs the pick. Every area file is `status: planned` with `verified_at: none` and no `sources`, "Where implemented" says "Not built yet.", and what the pitch leaves open is written as `Unknown`. Without a pitch the spec has one area named after the project.

`adopt-brownfield` proposes the areas from `codebase/architecture.md` and the docs index and confirms them in one question. The code under each area's `paths` is read against its description. An area is `implemented` or `partial` with `verified_at` only for what that read established; otherwise it is `planned`. An area with an authoritative document is pointer-only: frontmatter with `sources`, the four required sections and what the document lacks. For a project that has `.ytstack/` and no spec the skill writes only `spec/` and the missing codebase map files.

Both skills copy the "Keeping this true" block verbatim and run `ytstack-spec lint` on what they wrote. Each of the two eval cases gets a second outcome grader: `.ytstack/spec/SPEC.md` exists.
