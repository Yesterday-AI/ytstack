# M019-S01-T01 -- Task Plan

**Summary:** `metadata:` migration: ytstack's own frontmatter keys (`tier`, `version`, `kind`) move under the spec-sanctioned `metadata:` map in all 25 skills; the checker reads them from there and warns on the legacy top-level form.

## Files

- Modify: `bin/ytstack-check` (`parse_frontmatter` learns one level of nesting for `metadata:`; `skill_meta(fm)` helper; `check_skill` reads kind via it; WARN "legacy top-level tier/version/kind, move under metadata:"; WARN when `metadata.tier` or `metadata.version` is missing)
- Modify: `skills/*/SKILL.md` (25 files: frontmatter only)
- Modify: `docs/ux/skill-structure.md` (Frontmatter section)
- Modify: `tests/ytstack-check.test.sh` (fixture with legacy keys -> WARN; fixture with `metadata:` -> no WARN; clean tree has zero legacy warnings)

## What this does

Claude Code ignores unknown top-level frontmatter keys, but the Agent Skills spec only allows `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools` for portable skills and packaging/upload hard-errors on anything else. `metadata` is a free key/value map, so `tier`, `version`, `kind` live there from now on:

```yaml
metadata:
  tier: core
  version: 0.1.0
  kind: directive
```

The checker parser gets a nested-map branch (a key whose value is empty followed by lines indented two spaces with `key: value`) and `skill_meta(fm)` returns the merged view (metadata first, top-level as legacy fallback). The six wrappers that had no tier/version get `tier: core`, `version: 0.1.0`. The `kind: handoff` / `kind: quick` values on artifacts are unaffected (artifact frontmatter, not skill frontmatter).
