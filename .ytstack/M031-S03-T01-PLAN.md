## What this does

`yt_factory_notices <yt_dir> <toplevel>` sets `YT_FACTORY_NOTICES`, at most three lines, each only when it applies:

- risk: `.ytstack/spec/` exists, `merge_by` resolves to `risk`, and `spec/REVIEW.md` is missing or no area file allows `auto_merge: low` or `normal`. An explicit `merge_by: human` or `coordinator` is a choice and stays silent.
- PR watch: origin is a GitHub URL and `~/.ytstack/config` has no `pr_watch=` line (an explicit `pr_watch=off` is a choice), or it has `pr_watch=on` and the worker's heartbeat is missing or 10 minutes old or older.
- runtime: deploy evidence (a deploy configuration file at the toplevel or a workflow named `*deploy*`) without a "Release" section, or signal evidence (an incident record, a finding of a kind other than `review`, a Sentry configuration) without a "Signals" section. The sections come from `ytstack-runtime sections`.

`session-start` adds the lines to the state block when the payload `source` is `startup` or `clear` (or absent on a SessionStart), so a resume or a compaction does not repeat them; the hook stays read-only. `ytstack-upkeep` prints a "factory tools" section with the same lines and does not count them: a setting is not a finding, and a scheduled run must not raise a question for it every time.
