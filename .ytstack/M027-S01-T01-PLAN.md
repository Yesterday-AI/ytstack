## What this does

A finding is what a signal source of the project reported and an intake judged worth acting on. It is recorded once: one file per finding, `.ytstack/signals/F###-<slug>.md`, with the frontmatter `id`, `key`, `source`, `kind`, `state`, `first_seen`, `last_seen`, `count`, `ref`, `reopens` and the sections "What was seen", "Assessment" and "Next". `docs/ux/signal-format.md` fixes that format.

`bin/ytstack-signals new --source <name> --key <key> --title <text> [--kind <kind>] [--read-at <time>]` takes the raw sighting on stdin and decides by the key. No finding has it: a new file with the next id. An `open` or `planned` finding has it: `last_seen` and `count` change and the sighting is appended, the newest five stay. A `dismissed` one: `last_seen` and `count` change. A `fixed` one: a new finding with `reopens: <old id>`. The first word of the output is `new`, `seen-again`, `dismissed` or `regression`, then the id and the path.

`list [--state <state>]` prints tab separated lines, the open and planned ones by default. `set <id> --state <state> [--ref <ref>]` changes the state: `dismissed` takes its reason from stdin and stores it under "Assessment", `planned` needs a reference. `check` validates the files: ids unique and equal to the file name, keys unique among the findings that reopen nothing, at most one finding per key that is not fixed, listed `state` and `kind` values, a reference on a planned finding, well-formed times.

Every write goes through a temporary file in the same directory and holds a lock that the shell creates under noclobber, because two intake runs can overlap.
